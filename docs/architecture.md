# Architecture

How Jolta fits together. Decisions and their reasons live in `decisions.md`; this file describes the shape the code should have.

## Overview

```
 ┌──────────────────────────── Jolta.app (sandboxed) ─────────────────────────────┐
 │                                                                               │
 │  SwiftUI + AppKit shell (apple/App)                                           │
 │   sidebar · NSTableView message list · reader (one WKWebView) · compose ·     │
 │   Cmd+K palette · settings · agent approvals                                  │
 │        │  async calls, pages of rows             ▲  CoreEvent callbacks       │
 │        ▼                                         │                            │
 │  JoltaFFI Swift package (generated by UniFFI, Swift 5 mode)                    │
 │        │                                                                      │
 │  ┌─────▼──────────────── Rust core (crates/core) ───────────────────────────┐ │
 │  │ accounts/oauth ─ keychain                                                │ │
 │  │ sync: ImapEngine (Gmail, iCloud, Fastmail, IMAP) · GraphEngine (M365)    │ │
 │  │ store: SQLite (WAL) + blob files  ·  search: FTS5 + query language       │ │
 │  │ actions: optimistic apply + op queue + undo · snooze · outbox            │ │
 │  │ render: mail-parser → ammonia + CSS filter → safe HTML                   │ │
 │  │ mcp: server on a Unix socket, permissions, approvals, audit log          │ │
 │  └──────────────────────────────────────────────────────────────────────────┘ │
 │                                                     ▲ Unix socket (app group) │
 │  Contents/MacOS/jolta-mcp  (stdio ⇄ socket bridge) ──┘                         │
 └───────────────────────────────────────────────────────────────────────────────┘
        │ IMAP/SMTP (TLS)          │ HTTPS (Graph, OAuth)         ▲ stdio
        ▼                          ▼                              │
   Gmail, iCloud, Fastmail    Microsoft Graph, Google/Microsoft   AI agents (Claude
   and other IMAP servers     sign-in                             Code, Codex, ...)
```

The core owns all state. The shell renders what the core says and sends user intents back. Nothing in Swift knows what IMAP or Graph is.

Add a crate only when a milestone needs a separate binary. Modules inside `core` keep later splits cheap.

## Data model

One model covers Gmail labels, IMAP folders and Graph folders. A message belongs to one account and to any number of mailboxes.

| Table | Holds | Notes |
|---|---|---|
| `account` | id, kind (`imap`, `gmail`, `graph`), address, display name, server settings, sync state | Secrets are in the Keychain, keyed by account id. |
| `mailbox` | id, account, remote id or path, name, role (`inbox`, `sent`, `drafts`, `archive`, `trash`, `spam`, `snoozed`, none), per-mailbox sync cursor | The cursor is `UIDVALIDITY` + highest UID + `HIGHESTMODSEQ` for IMAP, or the delta link for Graph. Gmail labels are mailboxes too. |
| `message` | id, account, remote id, thread id, Message-ID, date, from, to/cc, subject, snippet, flags (seen, flagged, answered, draft), has attachments, size, blob hash, List-Id | Remote id is `X-GM-MSGID` for Gmail, the immutable id for Graph, and `mailbox + UID` for plain IMAP. |
| `message_mailbox` | message, mailbox, UID where relevant | The many-to-many link. Archive in Gmail removes the inbox row; in IMAP it is a move. |
| `thread` | id, account, latest date, subject, participants, unread count | Built from `X-GM-THRID` (Gmail), `conversationId` (Graph), or References / In-Reply-To with a subject fallback (IMAP). |
| `op` | id, account, kind, target ids, payload, state (`pending`, `sent`, `failed`), created, undo deadline | Every user and agent action. Applied to local tables at once, sent to the server by the sync engine, and safe to replay. |
| `snooze` | message or thread, wake time, original mailbox | The message moves to a server folder or label named `Snoozed`, so phones hide it too. The core moves it back at wake time. |
| `outbox` | draft blob, account, send-after time | Undo send is a delay: the message waits here for the undo window, then the engine sends it. |
| `section` | id, name, position, query | Split inbox sections are saved searches in the same query language as search. |
| `agent`, `agent_grant`, `audit` | MCP clients, their permissions, and every action they took | |
| `message_fts` | FTS5, contentless: subject, from, to, body text | Rowid is `message.id`. |

Raw RFC 822 messages are stored as files in the data folder (`~/Library/Application Support/Jolta/blobs`), named by SHA-256. The SQLite file sits next to them; see `decisions.md` for why the folder is not the app group container. Headers and snippets go to SQLite on first sync; bodies download on demand and in the background for recent mail.

## Sync

Each account runs one engine task on tokio. Both engines implement the same small interface.

```rust
trait Engine {
    async fn run(&self, ctx: SyncCtx) -> Result<()>;      // initial sync, then keep up to date
    async fn apply(&self, op: &Op) -> Result<OpOutcome>;  // push one queued local change
    async fn fetch_body(&self, msg: &MessageRef) -> Result<Blob>;
    async fn send(&self, draft: &OutboxItem) -> Result<()>;
}
```

- **Plain IMAP.** Sync INBOX first, newest messages first, so the list fills within seconds; other folders follow. Use CONDSTORE (`CHANGEDSINCE`) when offered, QRESYNC when offered, and otherwise a UID range fetch plus a flag sweep over recent UIDs. One extra connection holds IDLE on INBOX. A changed `UIDVALIDITY` drops and refetches that mailbox.
- **Gmail.** Same IMAP engine with Gmail mode on: sync `[Gmail]/All Mail` only and read labels from `X-GM-LABELS`, so a message in three labels is stored once. Thread ids come from `X-GM-THRID`. Gmail search operators can be passed to the server through `X-GM-RAW` when local search lacks the mail.
- **Microsoft Graph.** One delta query per mail folder with immutable ids, polled every 30 to 60 seconds and right after any local action. Sending uses `sendMail`; drafts use the drafts API. Throttling (HTTP 429) honours `Retry-After`. An admin-consent error during sign-in shows as a plain message with the tenant name.
- **Offline and failures.** Ops queue while offline and replay in order when the connection returns. A failed op is retried with backoff; after it fails for good, the local change is reverted and the UI shows why.

## The bridge to Swift

Keep the UniFFI surface small and coarse. Lists cross as pages, never whole mailboxes.

- `Core::open(data_dir, listener) -> Core`
- `accounts()`, `add_imap_account(...)`, `begin_oauth(provider) -> url`, `remove_account(id)`
- `query_count(query) -> u32` and `query_page(query, offset, limit) -> Vec<ThreadRow>` for any list: an account's inbox, the unified inbox, a section, a search
- `open_thread(id) -> ThreadDetail` with sanitized HTML per message
- `perform(action, target) -> UndoToken` and `undo(token)`
- `compose(...)`, `send(draft) -> UndoToken`
- `snooze(target, until)`, sections CRUD
- `vips()` and `set_vips(addresses, vip)`. Rows and reader messages carry a `vip` flag, and new-mail events say whether the sender is a VIP, so the app can limit banners to VIPs.
- `suggest_addresses(typed, account, recipients)`, `forget_address`, `set_address_book`: compose suggestions from people you sent to or replied to, ranked by how often and how recently, with mail from the chosen account counting double. The list is built from the store (about 80 ms for 23,000 sent messages), cached, and rebuilt in the background when older than two minutes. The app may hand over the Mac's Contacts as a lower-ranked source; they never leave the process.
- `unsubscribe(thread)` reads `List-Unsubscribe` from the message source and leaves the list: an RFC 8058 one-click POST when offered over HTTPS, else an unsubscribe email from the receiving account through the outbox, else the web page for the app to open.
- Message bodies cross the bridge as one string in a small Markdown subset (`rich.rs`: bold, italic, strikethrough, links, list and quote lines). The editor converts with `body_spans` and `body_markdown`; `compose::build` sends a plain-text part and an HTML part made from it. Each account's signature (`set_signature`) is in the same format, and `swap_signature` replaces it when the sender changes.
- `send(compose, send_at, remind_at)`: `send_at` holds the message in the outbox until then (the engine already wakes for the next queued send; `scheduled()` lists them, `cancel_send` takes one back for editing). `remind_at` stores a reminder by the message's Message-ID. When it is due and nobody but the user's own accounts has written in the thread since, the reminder fires: `CoreEvent::NoReply`, and inbox lists include the thread (`search::reminder_queries` reruns the list's query for that thread) until it is archived, trashed, moved or snoozed. Nothing changes on the server. Both need Jolta running at that time; otherwise they happen at the next launch.
- `reply_compose(thread, Forward)` saves the original's attachments under `<data dir>/forwards/<message id>/` and lists them on the compose. Images the HTML shows inline stay behind.
- AI (`core/src/ai`, bridge in `ffi/src/ai.rs`), off until the user picks a model in Settings › AI:
  - `ai_settings()`, `set_ai_settings(...)`, `set_ai_key(provider, key)`: the provider (this Mac, OpenAI or Anthropic), the model, an optional API address per provider and whether long conversations get a summary as they open. Settings live in the `setting` table under `ai`; API keys in the Keychain as `ai:openai` and `ai:anthropic`, never back across the bridge.
  - `ai_models(provider, url, key)` lists the provider's models and so checks the key and address. OpenAI-compatible servers use the Responses API (`POST {url}/responses`), Anthropic-compatible ones the Messages API (`POST {url}/v1/messages`), both streamed over server-sent events.
  - `local_models()`, `download_model(id)`, `pause_download(id)`, `remove_model(id)`: the catalog in `ai/local.rs` (Gemma 4 E2B, the default, and E4B), downloaded from Hugging Face into `<data dir>/models`, resumable with an HTTP range, renamed into place only after its SHA-256 matches. Progress arrives as `CoreEvent::ModelChanged`.
  - `summarize(thread, automatic, fresh, listener) -> AiTask` and `draft_message(compose, instruction, listener) -> AiTask` stream through `AiListener` (phase, all text so far, outcome); `AiTask.cancel()` stops them. `with_written(body, account, text)` puts a draft in front of the signature and quote.
  - Summaries are made only when a conversation is opened (automatically for 3 or more messages or 2,500 characters of text), never for old mail in bulk, and kept in `ai_summary` with the newest message they cover. A summary that new messages made stale is updated from the old summary plus the new messages: 1.5 s instead of 5.2 s for the 21-message test thread on the mini.
  - Sorting (`ai/triage.rs`): each incoming inbox message gets a category (personal, work, finance, newsletter, notification) and a needs-reply flag in `ai_triage`, once. The local model answers in two lines held to a GBNF grammar, about 0.4 s a message on the mini. `is:needs-reply` matches a conversation whose newest message was flagged and isn't answered; `category:<name>` matches a category. List rows carry `needs_reply` for the reply arrow. On by default for the model on this Mac, off for cloud providers.
  - Background queue (`ai/background.rs`): one job at a time, sorting before summaries. New mail queues its unsorted messages, and its conversation for a summary when that is long and the model is on this Mac. Every start, and switching sorting on, queue the unsorted inbox mail of the last 14 days. With the local model the queue waits while the app reports battery power, Low Power Mode or a hot Mac (`set_ai_background_allowed`, from `Power.swift`).
  - Search with AI (`ai/search.rs`, `ai_search_query`): ⌘J in the search field turns a request into a query in Jolta's search language, which replaces the typed text and runs over all mail. Relative dates ("last week", "vorige maand") are worked out in code and handed to the model, and the parser checks the answer, with one retry.
  - The local model runs in `jolta-ai`, which the core starts on first use and stops after 5 idle minutes. It speaks one JSON object per line over stdin and stdout (`load`, `generate`, `cancel`; `loaded`, `reading`, `text`, `done`, `error`); the core formats Gemma 4's chat prompt with thinking off. It inherits the app's sandbox and is built only for Apple silicon; on Intel it answers every request with an error and the settings offer the cloud providers.
- `CoreListener.on_event(CoreEvent)`: list changed (with query ids), sync status, new mail, agent approval request, errors

The Swift side keeps a page cache per visible list and asks for rows by index as the table scrolls.

## Rendering a message

1. `mail-parser` reads the raw message and picks the HTML part, or converts plain text to HTML.
2. `ammonia` strips scripts, event handlers, forms, iframes, objects, embeds, `javascript:` links and meta refresh.
3. Our CSS filter cleans `<style>` blocks and style attributes: no `@import`, no remote `url()`, no attribute-selector tricks.
4. Remote URLs are rewritten to `x-remote:` and inline parts to `cid:`. Remote images stay blocked until the user allows them for that sender or message; then the core fetches them without cookies or referrer and hands the bytes to the web view.
5. The web view loads the result with JavaScript off, subresource loading off, a CSP meta tag, a block-all content rule list, and a navigation decider that opens clicked links in the browser only after showing the real destination.

## Themes

The app draws with 16 color tokens (`ThemeTokens` in `apple/Jolta/ThemePalette.swift`). Graphite Dark and Graphite Light are written out by hand. The 23 Omarchy themes are mixed from Omarchy's `colors.toml` files, which `python3 scripts/omarchy-themes.py <omarchy checkout>` copies into the generated `apple/Jolta/OmarchyThemes.swift` with Omarchy's MIT notice; rerun it by hand when Omarchy changes. `ThemeStore` saves a dark and a light theme, and the Mac's appearance picks between them. A preview from ⌘K, Change Theme… takes the place of the theme of its own mode and forces that appearance on the app until it ends. Each `Theme` color is a dynamic `NSColor` that reads the active pair, kept behind a lock, every time AppKit draws it, so colors AppKit views already hold follow a change too. SwiftUI views draw again because reading a `Theme` color registers with the store. The reader gets the colors as CSS variables in a `<style id="jolta-theme">` that `ReaderPage` adds to each page it loads and replaces by script when the theme changes.

The empty inbox takes its colors from the theme too (`Scenery` in `apple/Jolta/Scenery.swift`): a sky and two hills for dawn, day, dusk and night, plus the bolt's colors. Each sky is mixed from the theme's own blue, cyan, green, magenta and orange toward its background or text color. A dark theme's sky stays dark at every hour, so an empty inbox never lights up a dark screen; the hour only tints it. A light theme gets the full day, pale by day and dark at night. Graphite Light keeps its hand-drawn skies. Contrast floors keep the words at 4.5:1 against the sky and the bolt at 4:1. The screen still draws with Core Animation layers and two small Core Graphics images, so a theme change only sets layer colors and redraws those two images.

## MCP

The core runs the MCP server and listens on `jolta.sock` in the app group container while the app runs. It speaks MCP's JSON-RPC directly (one message per line; `initialize`, `tools/list`, `tools/call`, `ping`) instead of using rmcp: tools are all Jolta needs, and the hand-written server avoids rmcp's fast-moving 3.x API. An agent's config points at `Jolta.app/Contents/MacOS/jolta-mcp`, which only copies bytes between stdio and the socket. Tools in the MVP are `search`, `read_thread`, `list_mailboxes`, `create_draft`, `label`, `archive` and `snooze`. Every tool result wraps email content in a block marked as untrusted data. Each agent has grants per account and per tool, and every call is written to `audit`. Sending is not an agent tool; an agent can only create a draft that the user sends.

## Tests

- **Unit tests** sit next to the code they check (`cargo test -p jolta-core`): the query parser, the sanitiser, MIME, AI answer parsing.
- **Regression and journey tests** live in `crates/ffi/tests/regression/` and run with `cargo test -p jolta-ffi --test regression`. Each test opens a fresh data folder in a temporary directory through the same `Core` the Mac app calls, adds accounts without a server (the engine starts no sync for them), imports messages written by the `Mail` builder in `fixture.rs`, and acts as the app would: list, open, archive, undo, reply, send, search. Secrets go to an in-memory store (`secrets::use_memory_store`), so no test touches the Keychain. The whole suite runs offline in well under a second.
- A test that needs state the app has no call for, such as an AI sorting result, writes it through a second `Jolta` handle on the same folder. The app's cached list order doesn't see those writes, so `App::list` pushes the cache out first.
- **Sync tests** (`sync.rs`) run the same app calls against a real IMAP server and SMTP catcher: Dovecot 2.4.5 and Mailpit 1.33.0 in Docker (OrbStack on the mini), started with `scripts/test-servers.sh up` and listening on 127.0.0.1 only. Any user name signs in to the test Dovecot, so each test uses a new one and starts with an empty mailbox. They cover the first sync, IDLE, actions and undo reaching the server, changes made elsewhere arriving, sending through SMTP with the Sent copy, snooze and drafts. Without the containers they skip; `JOLTA_SYNC_TESTS=1` makes a missing server a failure. They take about 20 seconds, mostly the 10-second undo-send window.
- **Live check** (`scripts/live-check.sh <address>...`) runs against real accounts, for what Dovecot can't stand in for: Gmail's labels and Microsoft Graph. Run by hand only. It copies the named accounts into its own data folder (`Jolta/LiveCheck`, same Keychain entries) so no other account syncs, refuses accounts with more than 500 messages, acts only on mail it sends to the account's own address with a random token in the subject, deletes nothing for good (its mail ends in Trash), and fails if any other message's folders or flags changed. Each step has a three-minute limit.
- **UI journeys** (`apple/JoltaUITests/`) drive the real app with XCUITest: archive and undo with keys, opening a conversation, the palette keeping the keyboard, search. Run them with `scripts/ui-tests.sh` (optionally naming tests). The test runner is sandboxed and can't write to Jolta's data folder, so the script fills one folder per test, `~/Library/Application Support/Jolta/UITest-<test name>`, from `Fixtures/` with the signed `jolta` CLI (`jolta dev local-account`, then `jolta import`), runs `xcodebuild test`, and removes the folders. Each test launches Jolta with `-JoltaTestData UITest-<test name>`; run without the script, the tests skip. The full log goes to `/tmp/jolta-ui-tests.log`. The journeys take over the screen's keyboard and mouse for about 30 seconds, and they share the debug app's preferences (such as the list's sort order) with Jolta builds run by hand on the same Mac. macOS needs Automation Mode allowed once per Mac, with an admin password: `sudo automationmodetool enable-automationmode-without-authentication`.
- Schema checks read the schema files themselves: a new `schemaN.sql` missing from `MIGRATIONS` fails `store::old_data_folders_upgrade`, and a new table with an `account_id` column is checked by `accounts::removing_an_account_leaves_nothing_behind` without editing the test.

## Performance budgets

Measured on Apple Silicon with the `jolta` CLI's synthetic mailbox until real mail is available.

- Cold start to a usable inbox: under 500 ms with 100k messages.
- Opening a cached message: under 50 ms.
- Search: p95 under 100 ms over 100k messages, results updating as you type.
- Memory: the app process under 150 MB with three accounts and one message open. WebKit's WebContent and GPU processes are measured and reported separately.
- The UI thread never waits on the network or on SQLite writes.
