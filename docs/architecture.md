# Architecture

How Jolta fits together: the shape the code should have.

## Overview

```
 ┌──────────────────────────── Jolta.app (sandboxed) ─────────────────────────────┐
 │                                                                               │
 │  SwiftUI + AppKit shell (apple/App)                                           │
 │   sidebar · NSTableView message list · reader (one WKWebView) · compose ·     │
 │   Cmd+K palette · settings · agent approvals                                  │
 │        │  async calls, pages of rows             ▲  CoreEvent callbacks       │
 │        ▼                                         │                            │
 │  JoltaFFI Swift package (generated by UniFFI, Swift 5 mode)                    │
 │        │                                                                      │
 │  ┌─────▼──────────────── Rust core (crates/core) ───────────────────────────┐ │
 │  │ accounts/oauth ─ keychain                                                │ │
 │  │ sync: ImapEngine (Gmail, iCloud, Fastmail, IMAP) · GraphEngine (M365)    │ │
 │  │ store: SQLite (WAL) + blob files  ·  search: FTS5 + query language       │ │
 │  │ actions: optimistic apply + op queue + undo · snooze · outbox            │ │
 │  │ render: mail-parser → ammonia + CSS filter → safe HTML                   │ │
 │  │ mcp: server on a Unix socket, permissions, approvals, audit log          │ │
 │  └──────────────────────────────────────────────────────────────────────────┘ │
 │                                                     ▲ Unix socket (app group) │
 │  Contents/MacOS/jolta-mcp  (stdio ⇄ socket bridge) ──┘                         │
 └───────────────────────────────────────────────────────────────────────────────┘
        │ IMAP/SMTP (TLS)          │ HTTPS (Graph, OAuth)         ▲ stdio
        ▼                          ▼                              │
   Gmail, iCloud, Fastmail    Microsoft Graph, Google/Microsoft   AI agents (Claude
   and other IMAP servers     sign-in                             Code, Codex, ...)
```

The core owns all state. The shell renders what the core says and sends user intents back. Nothing in Swift knows what IMAP or Graph is.

## Repository layout

```

crates/
  core/                 lib: all mail logic, modules listed below
  ffi/                  lib (staticlib): thin #[uniffi::export] wrappers over core

  mcp-bridge/           bin `jolta-mcp`: copies stdio to the app's Unix socket, nothing else
  ai-helper/            bin `jolta-ai`: runs a local model with llama.cpp, one request at a time
  uniffi-bindgen/       bin `uniffi-bindgen-swift`: writes the Swift bindings from the compiled library
vendor/llama-cpp-2/     llama-cpp-2 0.1.160 with a lazy-mode setter (see vendor/README.md)
apple/
  JoltaFFI/              Swift package: binary XCFramework + generated Swift (Swift 5 mode)
  Jolta.xcodeproj        hand-made project with buildable folders, no XcodeGen or Tuist
  Jolta/                 SwiftUI + AppKit sources (Swift 6 mode)
scripts/
  build-core.sh         cargo build (arm64; x86_64 too with JOLTA_INTEL=1), uniffi-bindgen-swift, xcframework;

```

Add a crate only when a milestone needs a separate binary. Modules inside `core` keep later splits cheap.

## Data model

One model covers Gmail labels, IMAP folders and Graph folders. A message belongs to one account and to any number of mailboxes.

| Table | Holds | Notes |
|---|---|---|
| `account` | id, kind (`imap`, `gmail`, `graph`), address, display name, server settings, sync state | Secrets are in the Keychain, keyed by account id. |
| `mailbox` | id, account, remote id or path, name, role (`inbox`, `sent`, `drafts`, `archive`, `trash`, `spam`, `snoozed`, none), per-mailbox sync cursor | The cursor is `UIDVALIDITY` + highest UID + `HIGHESTMODSEQ` for IMAP, or the delta link for Graph. Gmail labels are mailboxes too. |
| `message` | id, account, remote id, thread id, Message-ID, date, from, to/cc, subject, snippet, flags (seen, flagged, answered, draft), has attachments, size, blob hash, List-Id | Remote id is `X-GM-MSGID` for Gmail, the immutable id for Graph, and `mailbox + UID` for plain IMAP. |
| `message_mailbox` | message, mailbox, UID where relevant | The many-to-many link. Archive in Gmail removes the inbox row; in IMAP it is a move. |
| `thread` | id, account, latest date, subject, participants, unread count | Built from `X-GM-THRID` (Gmail), `conversationId` (Graph), or References / In-Reply-To with a subject fallback (IMAP). |
| `op` | id, account, kind, target ids, payload, state (`pending`, `sending`, `done`, `failed`), created | Every user and agent action. Applied to local tables at once, sent to the server by the sync engine, and safe to replay. The worker claims an op (`sending`) in the statement that reads it and marks it `tried`, which a failed attempt and a restart keep when they put it back to `pending`, so Undo drops only an op never tried and gives one that may have reached the server its opposite op, sent after it. |
| `snooze` | message or thread, wake time, original mailbox | The message moves to a server folder or label named `Snoozed`, so phones hide it too. The core moves it back at wake time. |
| `outbox` | draft blob, account, send-after time | Undo send is a delay: the message waits here for the undo window, then the engine sends it. |
| `section` | id, name, position, query | Split inbox sections are saved searches in the same query language as search. |
| `agent`, `agent_grant`, `audit` | MCP clients, their permissions, and every action they took | |
| `message_fts` | FTS5, contentless: subject, from, to, body text | Rowid is `message.id`. |

An `op` or `calendar_op` id is the app's Undo token, an `outbox` id its Undo send token and the reply an `invitation_answer` keeps, a `draft` id how the app and agents open and save a draft. These tables are `AUTOINCREMENT`, so a deleted row's id is never given to a newer row for a stale token to act on.

Calendars have their own tables (`calendar`, `event`, `occurrence`), written by `store/calendar.rs`. The views read only `occurrence`.

A series is one `event` row with an empty recurrence id plus one row per changed or cancelled occurrence, under the same UID with that occurrence's original start as recurrence id. `rebuild_series` takes the first row without a recurrence id as the master and ignores any other, so a changed occurrence stored without one disappears and its series keeps the old time. Microsoft 365 lists a series as instances with a UID each. The Graph source (`calendar/sources/graph.rs`) stores an exception under its master's UID, with `originalStart` read on the clock of the rule's `recurrenceTimeZone`, since Graph gives an all-day series UTC as its own zone. Graph's delta leaves `originalStart` out unless `$select` names it. The Graph docs say delta takes no `$select`, but Microsoft 365 honours it and keeps it in the delta link, so the delta round selects the same fields as the poll and costs no extra request. Delta reports a deleted series by its master's id alone, so a removal the server confirmed (`Removal::Deleted`: delta's `@removed`, Google's cancelled master, a CalDAV 404) also removes the rows filed under that id as their series (`master_id`). A master that a full listing leaves out, or that Graph refuses to give, leaves as `Removal::Unlisted` and keeps them, since the server may still list them. `sync::apply` stores a round's removals before its upserts, so an object the round returned is written back even when a removal in the same round took it. A meeting held in several shown calendars, as when the user invites another of their own accounts, is one occurrence in the views, and reminders, cards and the editor reach the same copy (`series::copy_rank`): the copy the user organizes the meeting in first (`organizer_is_me`), since a meeting Jolta made has a UID that names no provider, then the copy on the provider the UID comes from, the default calendar, and the calendar added first.

Status events (C4 U1). `EventData.kind` keeps what Google's `eventType` says beyond busy or free: out of office and focus time with what they decline (`AutoDecline`) and their message, focus time's Do not disturb, a working location (`Workplace`), and birthdays. Google reads them from `outOfOfficeProperties`, `focusTimeProperties` and `workingLocationProperties`; focus time stays busy and a working location free. Other sources say only `show_as` out of office, so they store no kind, and `EventKind::shown` makes one where a view reads it: the occurrence row (`json_extract` of `$.kind`, read with the row) and the event detail's line ("Out of office · declines new invitations"). A stored kind would go stale when the editor changes Show as. Google's API declines nothing on an out-of-office event created without `autoDeclineMode` (`declineNone`, measured 2026-11-08), unlike Google Calendar's form. Find a time's own row joins the stored occurrences with the provider's free/busy for the account's address; a provider block that the account's stored blocking occurrences cover completely is dropped (`freebusy::uncovered`), since Google gives the user's out of office as a plain busy block. Schema 33 lists Google calendars in full again so stored events gain their kind. The week view draws out of office as a solid band at 45 percent of the calendar's color, focus time with a moon after the title, and a working location as a label with a glyph in each of its days in the all-day strip, never as a block.

Other people's working hours (C4 U2). A `Schedule` carries the person's `WorkingHours` when the provider says: Microsoft 365's `getSchedule` gives each person's `workingHours` with their busy times, in their mailbox's Windows zone, so they cost no extra call; Google gives none. Hours on a clock Jolta can't place, or that end before they start, are none, and none constrains nothing. `suggest` takes `SuggestOptions`: with `respect_others_hours`, each known person's time outside their hours (`WorkingHours::off`, on their own clock) counts as taken, while the user's hours still set the days and windows. `availability::note` gives the line under a name: the shown days out of office ("Out of office Thu, Fri"), else their hours when they differ from the user's ("Works 09:00 to 15:00", with their city when the clock differs). The bridge's `PersonRow` carries the hours, the note and the shown time outside the hours, which the panel shades; the hours come back through `find_time_slots`. The panel's header has **Their working hours** (O) when anyone's hours are known. Google can mark a colleague's busy block as out of office from `events.list?eventTypes=outOfOffice` on their calendar, read beside `freeBusy`, but `READS_OUT_OF_OFFICE` keeps it off until a second Workspace user verifies that free/busy access is enough. `free-busy.json` takes `peopleHours` by address for the demo.

Automatic replies (C4 U3). `calendar::away` keeps each account's out-of-office auto-reply as its provider says, in `auto_reply` (schema 34): `AutoReply::Off`, or `On` with an open or set start and end, where the start counts and the end doesn't. Microsoft 365 reads and changes `mailboxSettings/automaticRepliesSetting` with the calendar sign-in's `MailboxSettings.ReadWrite`, so an account with calendar off has no row. Gmail's vacation responder is read with the mail scope through `gmail_settings`, which maps its own errors; changing it needs the restricted `gmail.settings.basic`, so Jolta links to Gmail's setting. A `Watcher` started with the calendar scheduler reads every account every 30 minutes and when asked (`check_away`: the app becoming active, calendar turned on or off), checks each minute whether what is on now changed, and sends `AwayChanged`. A read stamped earlier than the stored one never replaces it, so a refresh in flight can't undo Turn off. Turn off reads the setting first and sends only `status: disabled`, which keeps the messages; Exchange then shows a placeholder window of now to a day later (Microsoft 365 test account, 2026-11-08). The mail list shows a strip per account whose replies are on now (`away_states`); Settings › Calendar › Out of office lists every Google and Microsoft 365 account (`away_accounts`). `jolta cal away` prints each state. `away.json` in the data folder answers in place of the providers for the demo and UI tests.

Setting out of office (C4 U4, `calendar/away/plan.rs`). A `Request` names the accounts, an `Absence` (whole days on the Mac's clock, the last included, or two moments), the reply as text, who outside the organization gets it, and what Google declines. `targets` picks each account's own writable calendar: Google's primary one, which alone takes out-of-office events, else the default. `plan` is pure and says per account what happens (`Step`), which the sheet shows line by line: Microsoft 365 gets scheduled automatic replies (`PATCH /me/mailboxSettings`, the reply as escaped HTML for both audiences) and, since those block nothing in the calendar, an event shown as out of office, all day for whole days; Graph can't decline invitations for the user. Google gets an `outOfOffice` event through `Edit.extra` with `autoDeclineMode` sent explicitly, since the API declines nothing without it, and the reply as `declineMessage`; whole days run midnight to midnight on the Mac's clock, as Google refuses all-day ones, and the Gmail auto-reply is linked to. CalDAV calendars get an event with `X-MICROSOFT-CDO-BUSYSTATUS:OOF`. Each event carries Jolta's hold marker with the value `away` (`joltaHold`, Graph's `JoltaHold` property, `X-JOLTA-HOLD`). Google answers a status event the account doesn't offer with a 400 whose reason starts with `malformed`; its writer then creates the same event as a plain busy one (`refused_status_event`). `apply` sends the replies first, then queues the event through the op queue. The new event replaces the out-of-office events of its calendar that it overlaps (`replacing`): the first that can take the new days moves to them, and the others, such as Google's busy stand-in, go, so setting days again leaves one. A write merged after a 412 keeps the reply and declines just set (`merge::three_way` takes the user's new `kind`), so the retry sends them. Sync doesn't read markers yet, so Turn off finds out-of-office events by what they show as or by the title Jolta gives them, among the account's own guest-less single events (`away_events`). `ending` decides what Turn off ends: what is on now, shortened to this minute (an all-day event becomes timed from midnight), or deleted when nothing of it is left; with `Reach::NowOrNext`, as the sheet and Settings use, nothing on now ends the next out of office set and whatever overlaps it, deleted. The strip's Turn off uses `Reach::Now`, so it never ends a window set elsewhere since the strip read. The sheet opens from the palette (Out of office…), from Settings › Calendar › Out of office, and from the strip's Edit on Microsoft 365; each account row says what is set now with Turn off. `jolta cal away <account> --from … --until …` and `--off` do the same.

Rooms (C4 U5, `calendar/rooms.rs`). The picker offers rooms from two places. Microsoft 365's room lists come from the Places API (`sources/graph/rooms.rs`): every room, the room lists (usually buildings), and each list's rooms, so a room in no list shows too; a room marked `bookingType: reserved` is left out. They need `Place.Read.All`, which only a tenant admin can allow, so Jolta asks for it alone (`oauth::Ask::Rooms`, with the account's address) the first time the picker opens on that account. `account.rooms` (schema 35) keeps the answer: NULL never asked, `granted`, else Microsoft's reason for refusing, and the picker then offers Ask for access instead of opening the browser each time. The room lists' token has its own refresh (`oauth::Grant::Rooms`): Microsoft fails a whole refresh with AADSTS65001 when one scope it asks for has no consent (Microsoft 365 test account, 2026-11-08), so the account's mail and calendar refresh stays as it was. A refused token or a 401 or 403 from Places records the refusal. The lists are kept in `room` and read again when a day old, when the picker opens. Recent rooms work on every provider without a new scope: the room and resource attendees of the account's own meetings from 180 days back to 30 days ahead, the user's addresses never counted, most used first (`rooms::recent`). Booking a room is adding its address as a room attendee (C3's Room field), and `freebusy::room_schedules` asks `getSchedule` or `freeBusy` when it is busy, with no working hours. In Find a time, + Room (R) opens `RoomPicker.swift` over the panel: the Free filter on the picked time, a minimum size, rooms grouped by room list and then recent ones, a typed address, and a bar of the five hours around the meeting. An added room is one more row, drawn in its own color, and a busy room blocks a slot like a busy person. `rooms.json` in the data folder answers in place of Places, in the shape `directory` reads. `jolta cal rooms` lists them, asks with `--consent`, and says which are free with `--free`; `find-time` and `freebusy` take `--room`.

Invitations in mail (`calendar/invitation.rs`) get one `invitation` row per event that a message's `text/calendar`, `application/ics` or `.ics` part names: its UID, recurrence id, sequence, iTIP method and organizer, written whenever a body is stored (`store/invitations.rs`). A message reaches its event through the UID, so syncs that replace event rows need no update there. Bodies stored before this table existed get one background pass (`engine::scan_invitations`), for mail of the last 400 days. The reader builds an invitation card per event from the message itself (`calendar/card.rs`, HTML in `render/invitation.rs`): times in the Mac's zone, the answer from the calendar's copy, overlaps from `occurrence`, and a warning when the user never wrote to the organizer. Descriptions stay out of the card.

Answering (`calendar/respond.rs`) has one entry for the card and the calendar's detail. `plan` decides who tells the organizer from the source of the event's copy in the calendars of the account the invitation came to; another account's copy may be the organizer's own, when one of the user's accounts invites another. Only a copy in a calendar the account owns (`Calendar::is_own`) is answered through: a copy in a calendar shared with the account is its owner's, whom Google marks as the copy's `self`, so from mail the answer goes as without a copy, and the calendar's detail offers none. `rsvp::answer` refuses such a copy before any request, for the command line too. The card and the list read the user's answer from the same place: the copy in the account's own calendars, else the answer given from Jolta. A shared calendar's copy carries its owner's answer, so it never shows as the user's, and its cancelled copy doesn't mark the invitation cancelled.

| Copy | Reply | Don't send a reply |
|---|---|---|
| Google or Microsoft 365 | The provider answers and tells the organizer (`rsvp::answer`) | The provider answers without telling |
| CalDAV | The copy is answered with `SCHEDULE-AGENT=CLIENT`, then Jolta mails the iMIP reply: iCloud doesn't reply to an outside organizer | The copy is answered with `SCHEDULE-AGENT=CLIENT` |
| None, a feed or a calendar on this Mac | Jolta mails the iMIP reply | Nothing goes out |
| EventKit | Refused: macOS doesn't let apps answer for its calendars | Refused |

An answer through a copy whose server can't be reached, or while an op of that copy still waits, is kept in the store and queued as an `rsvp` op (`rsvp::answer_or_queue`, `Write::Answer`), behind the copy's other ops; a newer answer replaces one still waiting, and the worker sends it through the same `rsvp::answer`. The copy shows the answer and "Not synced yet" meanwhile; an occurrence without a row of its own gets its row only from the provider, since a row made here would send the answer to the series' object. The reply mail and `invitation_answer` go as for any answer, so the same answer again queues nothing. An answer can't be undone; one that fails for good lists its calendar whole on the next sync. A CalDAV answer is a PUT with `If-Match`, over the stored copy or, after a 412 or for a stored copy without an ETag, over the one fetched again. A server that gives that copy no ETag gets no write, and the answer fails with a message saying so.

The reply mail (`rsvp::imip_reply`) goes from the account the invitation came to, only to the organizer, through the outbox with no undo delay. It is built before the provider is asked, so an invitation Jolta can't reply to changes nothing anywhere. The reply answers only as that account, its address or an alias its calendar's copy marks as the user's, never as another of the user's accounts on the same invitation. Every answer is also kept in `invitation_answer` (account, UID, recurrence id), which the card shows when no calendar Jolta answers through holds the event; a whole-series answer replaces the ones kept for single occurrences. The organizer's cancellation of the whole event, newer than every invitation to it on the account, ends the answer and takes back its reply still waiting, so being taken off a meeting and invited again asks for a new answer. The row also keeps the note, the reply choice, the outbox row of the reply mail and the version answered: the event or occurrence, or a series with its changed occurrences, with only their SEQUENCE, times and repeat rule. The same answer again sends nothing new (a reply still waiting goes at once), and a changed one takes back a reply still waiting. An invitation to one occurrence without its series is always answered for that occurrence.

Propose new time goes through the same `respond::answer`, with a Maybe or a Decline and, for a series, for the occurrence the card shows; the card offers it for a timed meeting unless the invitation carries Outlook's `X-MICROSOFT-DISALLOW-COUNTER:TRUE` or the account's Microsoft 365 copy has `allowNewTimeProposals: false`. A Microsoft 365 copy is answered with `proposedNewTime`. Google's API has no proposals, so Google sends the answer and Jolta mails an iMIP COUNTER (`rsvp::imip_counter`); a CalDAV copy is answered quietly and the COUNTER follows; without a copy the COUNTER, which carries the answer as its PARTSTAT, is all there is. The COUNTER has the same Message-ID each time the same proposal is built, so asking again finds it in the outbox instead of sending it twice. On the organizer's side a COUNTER counts when it names the meeting's organizer, or names none, as Exchange's doesn't, for the user's own meeting, and comes from a guest of the account's calendar copy or the organizer's requests (`update::history`'s `not_from_guest`). Its card shows the proposed time, the meeting's time now and the proposed time's conflicts. A later version of the meeting outdates the proposal only when it moved the meeting, or cancelled it for the proposer or for everyone: a guest list changed for others raises SEQUENCE, on Exchange twice for a guest taken off and added again, without making the proposal stale. Decline proposal (`calendar/proposal.rs`) mails the guest a DECLINECOUNTER that answers the COUNTER's message in the outbox, which is how the card knows it went. Exchange drops the calendar part of a DECLINECOUNTER sent through Graph, so the guest of a Microsoft 365 organizer gets the words alone. Accept proposal (`proposal::accept_draft`, C3 U10) is offered while the account the proposal came to organizes the meeting and holds it in a calendar of its own, or in a calendar on this Mac that sends from it, which the store counts as the account's (`store::invitations::of_account`) (check 1): it opens the editor's draft of that copy at the proposed time, for a COUNTER with a RECURRENCE-ID that occurrence, found as a moment, where it is now (check 2), with "Bo Nilsson proposed this time: …" above the fields. Saving goes through the scope prompt, This event first, and Send an update? like any change of time. Whether a proposal was accepted isn't kept: the card reads Accepted, with no buttons, while the meeting in that calendar stands at the time proposed (`card::taken`), also once the server's version with a higher SEQUENCE is back, so a second Accept sends nothing (check 4) and Undo offers the proposal again. A proposal card shows no answer of the user's.

The message list marks a conversation that carries an invitation (`store::thread_invitations`, one statement per page of rows). The invitation it shows is its newest message from the organizer, else its newest reply. A request or cancellation that isn't from the meeting's organizer, by the card's rule (`update::organizer` and `update::sent_by`), is passed over: a conversation with nothing else shows the mark alone, and it cancels nothing elsewhere. A request shows the answer its card shows (`store::shown_answer`), for a series the answer to the occurrence the card shows, the next one still to come (`series::shown_occurrence`, from the events the `timing` column keeps, and the calendar's copy of that occurrence before the series' copy). A calendar copy's answer, and one given from Jolta, holds only for the version and the occurrence it went to, by one rule (`update::holds`), in the list as on the card. The list shows "Not answered" while its event is still to come, and the mark alone once it has passed unanswered; a cancellation, or a request whose event or series the organizer cancelled on the same account with the same or a later SEQUENCE, by mail or in the account's calendar copy (`update::cancels`, the card's rule, by which Graph's cancelled copy covers every SEQUENCE), shows "Cancelled", also when the occurrence shown has a copy of its own; replies and the user's own meetings show the mark alone. Each `invitation` row keeps when its event ends (for a series its last occurrence, or never for a rule without UNTIL or COUNT). `is:invite` finds the conversations whose invitation shows "Not answered" (`store::unanswered_threads` asks `thread_invitations`), so `-is:invite` finds exactly the others. An answer or a calendar change drops the app's cached list order and redraws the list, and so does the moment a "Not answered" event ends or a series moves on to its next occurrence (`store::next_invitation_change`), through a timer in the bridge. On the Mac mini's copy of a 168,000-message store, the first page of all mail took 0.84 ms p95 before and 0.87 ms after; a conversation with an invitation costs about 9 µs more, and one showing a repeating request about 18 µs more again, for placing its occurrences. Asking who sent each request, about 45 µs for a request from someone else, took a conversation with an invitation from 9 to 14 µs on average and `is:invite` from 0.15 to 0.29 ms p95 on that store; the user's own meetings skip it.

An organizer's update is a new invitation mail with the same UID (`calendar/update.rs`). Versions are ordered by SEQUENCE, then DTSTAMP. Only the meeting's organizer makes versions: the organizer is the one on the account's calendar copy, else on the first request for the UID to arrive, by the date the server received it, that came from its own organizer, and a mail counts when it names that organizer and comes from that address, from `calendar-notification@google.com` or iCloud's `noreply@email.apple.com`, or, for the user's own meeting, from another of the user's addresses. A request or cancellation without an ORGANIZER fails it. A message that fails this changes no other card or list entry, shows no answer, offers no answers or removal, and its card says "This isn't from the meeting's organizer". The card compares a message with the account's other mails for the same event or occurrence (`invitation` rows, bodies read from the blob store), with cancellations of the whole series for an occurrence, and with the account's calendar copy. A newer version in either makes the card say so, with no answers, conflicts or Join: a copy with a higher SEQUENCE whatever it changed, and a cancelled copy as a cancellation (on Graph, which keeps no SEQUENCE, only that). An occurrence's invitation also reads as cancelled once the copy of its series is cancelled. Otherwise the version before it is the latest earlier request, or the copy while its SEQUENCE is lower (on Graph another time counts, and only while no newer mail exists). Repeat rules compare by meaning (`recur::same_repeat`), so Graph's rule without `INTERVAL=1` equals the mail's with it, and two UNTILs that keep the same last occurrence are equal. For an occurrence moved for the first time, it is where the series had that occurrence. The card strikes through what changed against that version (`Changes`): the time, keeping the day when only the time moved and the other way round, the repeat rule, the place and the meeting link. An answer given to an earlier version holds unless the time, the day or the repeat rule changed since (`update::answer_holds`). A provider copy is judged against its own SEQUENCE, so after a sync it shows what Google or Microsoft 365 decided, and both reset answers on a move. An answer kept in `invitation_answer` is judged by the version it went to, which the row keeps, with a reply mail or without one; answers kept before the row had it hold. An answer shown on an occurrence of a series holds only while that occurrence stays where the version answered had it, each version placing it at its own changed occurrence when it has one, else at its series' time moved there (`series::occurrence`), so an update that leaves out an occurrence moved before reads Not answered; an answer to the whole series also needs the series' time and repeat rule unchanged.

A cancellation's card offers Remove from calendar while the receiving account's calendar holds the event, or the cancelled occurrence, uncancelled, as the user's copy as a guest: in a calendar the account owns (`Calendar::is_own`: on CalDAV, one whose DAV:owner is the account's principal, else one with the `all` privilege that Calendar Server's `shared` resourcetype doesn't mark as shared to the user; on Microsoft 365, one whose Graph `owner` is the account; on Google, only the primary calendar, whose id is the account's address, since Google gives a calendar shared with "Make changes and manage sharing" the owner role), listing the user as an attendee, and organized by someone else than the account or an alias the copy or the CalDAV principal names. Deleting the organizer's copy on Microsoft 365 would cancel the meeting for every guest, so `remove::guest_copy` refuses it before any request. `calendar/remove.rs` routes it per provider. Google and Microsoft 365 are asked first and only resynced when they already removed or cancelled the event, which both do within a minute. Otherwise the copy is deleted with `sendUpdates=none` on Google or a plain DELETE on Graph. A CalDAV copy gets SCHEDULE-AGENT=CLIENT on its ORGANIZER, then a DELETE, or an EXDATE for one occurrence, each with `If-Match`, so a scheduling server tells nobody. A 412 from any provider means the copy changed since Jolta read it, perhaps reinstated, so Jolta resyncs the calendar and says "The meeting changed; check it again" instead of trying again. Every CalDAV write carries an ETag. A copy fetched again, because the stored one has no ETag or the PUT returned none, is deleted only while it keeps the SEQUENCE and status Jolta read, and a server that gives no ETag gets the copy left alone with a message saying so.

Add to calendar (`calendar/add.rs`) puts an invitation into a calendar the user picks when the account it came to has no copy, as for an iCloud account whose calendar is off in Jolta. The card offers it only on the organizer's newest request that it offers answers on, and nothing is ever added without the user asking. The menu lists every shown calendar on any account that Jolta can write to (`add::choices`), except one that already holds the UID and those of the account that organizes the meeting; its default is the calendar last added to, else the default calendar. From then on that organizer is the meeting's for the receiving account (`update::organizer`), whatever other mail remains. The copy is that object: its series or single event by the object's id, its changed occurrences in the same CalDAV resource or filed under that id by Google's `recurringEventId` or Graph's `seriesMasterId` (`store::of_copy`, kept on each stored event as `master_id`), and once the object is gone the copy is gone. Update, an answer that follows and Remove reach it by the id recorded for it (`rsvp::target_of` with the object), so another event with the UID in that calendar is never the one written to. An added copy is never an account's own copy, also in the receiving account's own calendar (`store::stored_event` with an account), so it never decides the organizer or routes an answer through its provider. Google takes the newer version by a second import, CalDAV and Graph by a write, each with `If-Match`, and Update never writes over a change Jolta hasn't read, also to an occurrence it holds unchanged. On Google a private copy's series and each changed occurrence have an ETag of their own, an occurrence without an event of its own carries the series' ETag, and an import of the series changes only the series' ETag. So one listing by `iCalUID` first checks every event the update writes against what Jolta holds, then each import carries its event's ETag, or the series' as it stands for an occurrence without an event of its own. On Microsoft 365 every event of a series shares one change key, which any change to the series or an occurrence replaces, and Exchange replaces the key a write returns again right after it. So the first write carries the key Jolta read and each later one the key listed with its occurrence just before. Patching a series with a changed repeat pattern makes Exchange delete its changed occurrences. A copy that changed since Jolta read it is left alone with "The meeting changed in your calendar". Neither provider writes a series and its occurrences in one step, so a 412 from a change made during the update can still come after the series was written; the update stays offered. Microsoft 365 takes a repeating meeting only when Graph's pattern repeats on the same days as its rule over four years, so a monthly one on the 29th to the 31st is refused. The answer still goes by mail from the receiving account; afterwards the copy follows quietly (`add::follow`): the user's PARTSTAT on CalDAV, the calendar owner's entry on Google, the free, tentative or busy time on Graph. A copy added after answering gets that answer. Remove from calendar counts the added copy as the user's whoever it names as organizer, and the calendar's detail offers no answers on it.

File responses automatically (`calendar/filing.rs`), off until the user turns it on in Settings › Calendar, archives a guest's reply to a meeting the receiving account organizes when the reply says nothing beyond its answer. A reply says nothing more when it answers as one guest, its COMMENT or X-RESPONSE-COMMENT is blank, and every body a reader could see, text and HTML, is its producer's by PRODID: empty only from Exchange, one sentence from Apple and Jolta, and from Google its sentence above lines that are each the event's own title, place or description, Google's labels and links, the time, the guest list or a footer seen in real Google replies (`filing/google.rs`). Each guest-list line must name the reply's organizer or guest, or someone the account's copy of the meeting names, by name or address. No line may be quoted. An HTML body may show no image the reader would show, no SVG, picture, data URI or inline part, and hold no word more often than the text body, apart from the labels Google's HTML adds to Google's text; under Exchange's empty text the HTML must be empty too. The words are judged once the meeting is placed, since Google's guest list needs the account's copy. Of the 58 replies from other people in a real store, 50 passed: five carried a note, a mailer's own words or a mailer Jolta doesn't know, two answered a weekly series Google described in Russian, and one listed guests that no invitation in that store names, which the account's calendar copy would. Answering takes its aliases the same way. The reply counts when it comes from its guest's own address or Google's and `update::from_guest` finds that guest on the meeting, a changed occurrence's own guests included. The pass archives the replies that pass in one move op from the inbox to the archive, the one the E key queues but for those messages alone, and the app shows its toast with Undo (`CoreEvent::ResponsesFiled`). A reply whose meeting or guest the account can't place yet, as before the calendar's copy of a new meeting has synced, is looked at again for a day after it arrived, then kept.

Calendar edits have an op queue of their own (`calendar/ops.rs`, `store/calendar_ops.rs`, table `calendar_op`). A request that never reached its server (`Error::Offline`: no connection, name lookup or proxy, the token refresh included) puts the op back for a minute without using up an attempt, so an op waits out any time offline. `ops::queue` writes the edit into `event` at once, rebuilds that series' occurrences, sets `event.changed_locally` (the "not synced yet" mark) and stores an op with the version it writes over (`Held`: the remote id and ETag) and the key a retried create reuses: Google's event id from the UID, Graph's `transactionId`, the CalDAV resource name. Nothing waits on the network. The calendar scheduler sends due ops between its sync rounds (`ops::run_due`), one at a time per event and up to four events at once; a claimed op counts as tried. Undo drops an untried op and puts the store back, and queues the opposite of a tried one that emailed nobody. Five failed attempts put the store back to the server's version. A local calendar's store is its server, so its ops only carry undo. `calendar/caps.rs` says what Jolta can do with each calendar, `change::classify` sorts a change into what guests hear about and the user's own fields, and `merge::three_way` merges two edits field by field.

Each source has a writer next to its reader (`sources/google/write.rs`, `graph/write.rs`, `caldav/write.rs`): a create, an update and a delete. Google and Graph get a PATCH of the changed fields only; CalDAV gets a PUT through `ical_edit` onto the stored text, so lines Jolta doesn't model stay. Every update and delete carries the held ETag. A 412 fetches the server's version and merges the edit into it, for up to three rounds; a field both sides changed keeps the server's value and the op ends in `conflict`, which the detail shows with Apply mine. A 404 or 410 ends the op as `gone`: the event leaves the store and is never recreated. A sync leaves the rows of an op still to send alone. `Edit.extra` passes provider fields Jolta doesn't model into the request untouched, and each writer refuses a field it can't hold.

Meetings the user organizes (C3 U5a). An op's `notify` (`all`, `outside`, `changed`, `none`) reaches the writer as `Tell` with the user's message: Google gets it as `sendUpdates` (`all`, `externalOnly`, `none`; new people only is `all`, since Google mails only the guests a change of people adds or removes), Microsoft 365 always mails the guests of a meeting's own fields and cancels a meeting with guests through `POST /cancel` with the message as its comment, after comparing the change key because `/cancel` takes no If-Match, and a CalDAV server with scheduling mails them itself on a plain PUT or DELETE, Jolta adding the user as ORGANIZER to a resource that gets its first guests. Who the user is comes from `draft::mine`: the account's address, and in a calendar the account owns the attendees the calendar marks as the user. An op that mails waits the 10-second undo window and can't be undone once tried, so a retry after a lost answer meets its own change as a 412 and writes nothing more.

`change::dialog` builds Send an update? from `change::classify` and the calendar's `caps`: Google offers Don't send, Keep editing, Send and "Only guests who don't use Google Calendar"; Microsoft 365 and iCloud say they will email the guests and offer Keep editing and Send; a change of people alone names who gets an invitation or a cancellation and sends to them only; a calendar on this Mac offers Don't send, Keep editing and Send, names the address Jolta sends from and has a message field. `change::cancel_dialog` builds Cancel the meeting?, with a message field only where the cancellation carries one (Microsoft 365). `draft::plan_save` and `plan_delete` return these dialogs, a guest's delete returns Decline and remove? instead, and `save_draft` and `delete_drafted` take only a notify one of the dialog's buttons offered. Meetings in a calendar on this Mac (C3 U5b, `calendar/organizer.rs`) are mailed by Jolta itself as iMIP (RFC 6047). The calendar sends from one of the user's accounts (`calendar.send_from`), which the editor asks for once, through `SavePlan.senders` or `DeletePlan.senders` and `set_send_from`, and Settings › Calendar changes; that address is the user in the calendar (`store::calendar_address`). `ops::queue` makes the sending account the organizer of a new meeting, raises SEQUENCE for a new time, day, repeat rule, place, title, description, status or guest list, and on a new time or repeat rule that goes to the guests resets their answers, except for a series that only ends sooner, as This and following leaves the old one: every occurrence left is one they answered, Google keeps those answers too, and a Microsoft 365 guest keeps its own without replying again. A series' update carries its changed occurrences. The mails go through the sending account's outbox at once, linked to the op (`calendar_op.outbox`); each Message-ID comes from the op, the event's version and the guest, so an op tried again after a crash finds its mails there. The scheduler then wakes that account's mail worker. After each mail sync, `organizer::read_replies` takes the guests' iMIP REPLYs to the account's meetings into the event: only for a meeting the account organizes in a calendar on this Mac (check 1), on the occurrence the RECURRENCE-ID names as a moment, making its row from the series when it has none (check 2), from the guest's own address or Google's for its users (check 3), and only when newer by DTSTAMP than the last answer taken from that guest there, kept in `guest_reply` (check 4). CalDAV servers without scheduling would use the same path once Jolta reads `calendar-auto-schedule`; until then every CalDAV calendar counts as one that schedules.

The event editor's model is `calendar/draft.rs`. A change to one occurrence of a series is saved for the scope the user picks from `plan_save`'s choices, each saying what it costs there ("Starts a new series from Tue 24 Nov.", "Removes the changes made to 3 single events."). `description::split` keeps a Teams, Meet or Zoom block byte for byte after the user's text, a room is a `Role::Room` attendee whose address fills an empty location, and `quick::time` reads the time fields ("930", "14:30", "2pm", "9u30"). `draft_for_copy` makes ⌘D's and ⌥-drag's new event from an occurrence: its time, title, place, description and the user's own settings, without the people, the repeat or the meeting, so a copy mails nobody; a location or description line that names the meeting's link, ID, passcode or dial-in number is left out.

Email guests (C3 U10, `calendar/emailing.rs`) is a mail, not a calendar update: compose from the event's account (a calendar on this Mac: the account it sends from) to everyone on it but rooms and the user, who is the calendar's account with the aliases it marks and never another account of the user's (check 1), the organizer first, "Re: <title>", and a first line naming the event and its time here, with the meeting's join link on the next line. Moving between calendars (C3 U9, `calendar/moving.rs`). `moving::plan` decides from the two calendars and the series' rows whether and how an event moves, and says why when it doesn't: within one account Google gets `events.move` and CalDAV a MOVE, which keep the server's object (`How::Native`); Microsoft 365, which has no move, and any two accounts or a calendar on this Mac get a create in the other calendar and then a delete (`How::Copy`). A meeting with guests moves only where nobody hears of it: iCloud's MOVE mailed neither guest, and an update after it reached both as usual (iCloud test account, 2026-11-08), so `caps.move_meetings` is true there alone. Microsoft 365 refuses ("Moving this meeting would send your 6 guests a cancellation and a new invitation, and lose their answers."), as does any copy across accounts and anything into or out of this Mac; Google refuses until its move of a meeting is measured. Someone else's meeting stays in the calendar the invitation reached (check 1). A copy leaves behind the user's own attendee entry, the organizer and the series ids of the old account, and the call the old server made: a Teams meeting moved to Google loses its block, said before the move, and one moved to another Microsoft 365 calendar asks for a new Teams meeting. The whole series always moves. A move is one op, `Write::Move` with the rows as they were and the events the other calendar gets, filed under the calendar it goes to, where the event is from then on: `queue` moves the rows at once, a later edit there waits for it, and it waits for the edits still to be sent where the event was (`READY`); `HELD` keeps a sync of either calendar from bringing the event back or taking it away while it waits. Google's move takes no version and iCloud's MOVE ignores If-Match (iCloud test account, 2026-11-08), so both writers read the object first and move it only at the version held; an object no longer there is looked for in the other calendar, where a retry finds what its first try moved. A copy creates at the op's key, so a retry finds the event its first try made, and deletes the original only after that, held to its version; a change made to it meanwhile leaves it where it was (`Sent::Stayed`) and deletes the copy again, as does a deletion meanwhile. Undo puts an untried move back and moves a sent one back. The editor's picker lists every calendar with `move_choices` (refusal or cost); saving a draft with `move_to` queues the move, then the other changes as an edit in the new calendar that waits for it (`ops::queue_after`), so one Undo takes back both. `jolta cal move` does the same.

Quick create (`calendar/quick.rs`) reads a line such as "Lunch with Jan fri 12:30 at Mok" in English, Dutch and French and keeps the reading that turns the most words into fields, a tie going to the app's language, then the Mac's. Each language is a `Words` table; a first pass takes repeat phrases ("every other friday", "om de twee weken", "un vendredi sur deux"), so "until 18 dec" or "for 10 weeks" later in the line ends a rule rather than making a range, and a second pass takes days, times, ranges, lengths, zones, people and places left to right. A field already filled refuses a second value, which then stays in the title and in `leftover` with the other date-like words. "fri" is the coming Friday, "next fri" the Friday of next week, and a bare hour from 1 to 7 is the afternoon (`quick::time`, which the editor's time fields use too). A parse takes 20 to 80 µs in a release build. `quick::draft` makes the editor's draft from it: a name becomes a guest only when exactly one person the user has written to (sent mail or replied, never an address-book entry alone) has it as a whole word (`People::resolve`); any other name waits in `EventDraft.unresolved`, which `check_draft` blocks on, so a guess never sends an invitation. With AI on, `ai/quick.rs` asks the model when the parser left date-like words or found no day or time in a line with digits: the request carries now, the zone and the next 21 days with their weekdays, the answer is a JSON object held to a grammar on the local model, and Rust checks each field (a start from yesterday to two years ahead, on the weekday the line names, an end after it, at most 14 days timed, a known zone, an RRULE the calendar holds) and drops what fails, with one retry when the day was refused. The model's day replaces the parser's only when the parser left words; the whole wait is 5 seconds, after which the editor opens with the parser's reading. `G` reads a day with the same rules, except that a day and month without a year is the nearest one, past or future.

Repeating events (`calendar/repeat.rs`, `calendar/split.rs`). The repeat editor's presets come from the event's own date and are greyed where the calendar can't hold them (`repeat::refusal`: Google and Microsoft 365 take no rule more often than daily, and Google drops BYHOUR; Microsoft 365 takes only what Graph's pattern repeats the same way). The draft keeps the series' rule beside the occurrence it opened. This event is an `Update` of the occurrence: one without a row of its own (`fresh`) is written as an instance of its series, guarded by the series' version, which Google and Microsoft 365 share between a series and its instances: Google's id for it is the series' id and the start in UTC, Microsoft 365's is found among the series' instances by `originalStart`, and CalDAV gets a VEVENT of its own in the series' resource. A changed instance lands under its own id; Graph's PATCH answer leaves out `originalStart`, so the instance is read back, and an occurrence's op never lands a version that doesn't name its occurrence. All events changes the series, its time moved as far as the occurrence's was, and reaches each changed occurrence for the fields it kept the series' value of (`change::carried`); the changed occurrences the new time or rule no longer holds leave with it as `dropped` rows, and on Microsoft 365 every one once the time or pattern changes, or a series that counted its occurrences ends on a day, as Exchange deletes them then. Google drops them on a new time too. This and following (`split::queue_following`) is two ops: a create of the new series under a new UID from the occurrence on, with the old series' later changed occurrences carried over (Google and Microsoft 365 write them as instances after the create) and its later EXDATEs, and an update that ends the old series the day before (UNTIL in UTC, as Graph's range end can say), which waits for the create (`after`). A failed create fails the update and puts the old series back, so a failure can show both series for a while but never neither. Deleting one occurrence is a `Cancel`: the store adds an EXDATE and drops the occurrence's row, Google and Microsoft 365 delete the instance, CalDAV writes the EXDATE into the resource; Exchange deletes an instance whatever change key If-Match names, so the writer compares the key first. Writes that take occurrences out (a cancel, dropped rows, a split) wait the 10-second undo window and can't be undone once sent: Microsoft 365 can't bring an occurrence back.

Raw RFC 822 messages are stored as files in the data folder (`~/Library/Application Support/Jolta/blobs`), named by SHA-256. The SQLite file sits next to them, outside the app group container, because macOS keeps the unsandboxed `jolta` CLI out of that container; the sandboxed app reaches the folder through a `home-relative-path` exception. Headers and snippets go to SQLite on first sync; bodies download on demand and in the background for recent mail.

## Sync

Each account runs one engine task on tokio. Both engines implement the same small interface.

```rust
trait Engine {
    async fn run(&self, ctx: SyncCtx) -> Result<()>;      // initial sync, then keep up to date
    async fn apply(&self, op: &Op) -> Result<OpOutcome>;  // push one queued local change
    async fn fetch_body(&self, msg: &MessageRef) -> Result<Blob>;
    async fn send(&self, draft: &OutboxItem) -> Result<()>;
}
```

- **Plain IMAP.** Sync INBOX first, newest messages first, so the list fills within seconds; other folders follow. Use CONDSTORE (`CHANGEDSINCE`) when offered, QRESYNC when offered, and otherwise a UID range fetch plus a flag sweep over recent UIDs. One extra connection holds IDLE on INBOX. A changed `UIDVALIDITY` drops and refetches that mailbox.
- **Gmail.** Same IMAP engine with Gmail mode on: sync `[Gmail]/All Mail` only and read labels from `X-GM-LABELS`, so a message in three labels is stored once. Thread ids come from `X-GM-THRID`. Label… adds a label as a move from All Mail that keeps the All Mail link and takes one off as a move back into All Mail, so Gmail gets `+X-GM-LABELS` or `-X-GM-LABELS` by All Mail UID, undo is the opposite move, and the conversation stays in the inbox. Other accounts have no labels (`AccountKind::has_labels`): the L key says so and the palette leaves Label… out. Gmail search operators can be passed to the server through `X-GM-RAW` when local search lacks the mail.
- **Microsoft Graph.** One delta query per mail folder with immutable ids, polled every 30 to 60 seconds and right after any local action. Exchange keeps only the last few generations of a delta link, so a link a second copy of the store moved on, or one that expired, answers 410 SyncStateNotFound; that folder then lists itself again from the start in the same sync, keeping the rows of messages Graph still lists and taking out the ones it leaves out. Sending uses `sendMail`; drafts use the drafts API. Throttling (HTTP 429) honours `Retry-After`. An admin-consent error during sign-in shows as a plain message with the tenant name.
- **Offline and failures.** Ops queue while offline and replay in order when the connection returns. A failed op is retried with backoff; after it fails for good, the local change is reverted and the UI shows why.

## The bridge to Swift

Keep the UniFFI surface small and coarse. Lists cross as pages, never whole mailboxes.

- `Core::open(data_dir, listener) -> Core`
- `accounts()`, `add_imap_account(...)`, `begin_oauth(provider) -> url`, `remove_account(id)`
- `query_count(query) -> u32` and `query_page(query, offset, limit) -> Vec<ThreadRow>` for any list: an account's inbox, the unified inbox, a section, a search
- `open_thread(id) -> ThreadDetail` with sanitized HTML per message
- `perform(action, target) -> UndoToken` and `undo(token)`
- `thread_labels(thread)`: a Gmail account's own labels, marked when the conversation has them, for Label…
- `compose(...)`, `send(draft) -> UndoToken`
- `snooze(target, until)`, sections CRUD
- `vips()` and `set_vips(addresses, vip)`. Rows and reader messages carry a `vip` flag, and new-mail events say whether the sender is a VIP, so the app can limit banners to VIPs.
- `suggest_addresses(typed, account, recipients)`, `forget_address`, `set_address_book`: compose suggestions from people you sent to or replied to, ranked by how often and how recently, with mail from the chosen account counting double. The list is built from the store (about 80 ms for 23,000 sent messages), cached, and rebuilt in the background when older than two minutes. The app may hand over the Mac's Contacts as a lower-ranked source; they never leave the process.
- `unsubscribe(thread)` reads `List-Unsubscribe` from the message source and leaves the list: an RFC 8058 one-click POST when offered over HTTPS, else an unsubscribe email from the receiving account through the outbox, else the web page for the app to open.
- Message bodies cross the bridge as one string in a small Markdown subset (`rich.rs`: bold, italic, strikethrough, links, list and quote lines). The editor converts with `body_spans` and `body_markdown`; `compose::build` sends a plain-text part and an HTML part made from it. Each account's signature (`set_signature`) is in the same format, and `swap_signature` replaces it when the sender changes.

## Rendering a message

1. `mail-parser` reads the raw message and picks the HTML part, or converts plain text to HTML.
2. `ammonia` strips scripts, event handlers, forms, iframes, objects, embeds, `javascript:` links and meta refresh.
3. Our CSS filter cleans `<style>` blocks and style attributes: no `@import`, no remote `url()`, no attribute-selector tricks.
4. Remote URLs are rewritten to `x-remote:` and inline parts to `cid:`. Remote images stay blocked until the user allows them for that sender or message; then the app's `x-remote:` scheme handler fetches them over http or https with an ephemeral `URLSession`, without cookies, cache or referrer, and hands the bytes to the web view.
5. `ReaderPage` (`apple/Jolta/Reader.swift`) loads the result into one reused `WKWebView`, hosted in SwiftUI by an `NSViewRepresentable`, with JavaScript off on every navigation, a non-persistent data store, `securityRestrictionMode = .maximizeCompatibility` on macOS 26.4 and later, a CSP meta tag, a block-all content rule list, and a navigation delegate that cancels everything after the first load and opens clicked links in the browser only after showing the real destination. No page opens a window.
6. The app's own scripts still run with the page's JavaScript off. `callAsyncJavaScript` in the page world sets the theme, the expanded messages and the invitation cards. A user script in the app's own script world (`.defaultClient`) reports each expand and collapse, and the link under the pointer on each `contextmenu` event. WebKit dispatches that event before it asks the app to show its context menu, so `ReaderWebView.willOpenMenu` already knows the link and swaps WebKit's items for Jolta's: Open Link… and Copy Link on a link, then Copy and the image items.

## Themes

The app draws with 16 color tokens (`ThemeTokens` in `apple/Jolta/ThemePalette.swift`). Graphite Dark and Graphite Light are written out by hand. The 25 Omarchy-format themes are mixed from Omarchy's `colors.toml` files, which `python3 scripts/omarchy-themes.py <omarchy checkout>` copies into the generated `apple/Jolta/OmarchyThemes.swift` with Omarchy's MIT notice; rerun it by hand when Omarchy changes. The script also reads `scripts/themes/`, which holds themes Omarchy doesn't ship in Omarchy's format: Catppuccin Frappé and Macchiato, from Catppuccin's palette with its MIT license, mapped onto Omarchy's names the way Omarchy maps Mocha. `ThemeStore` saves a dark and a light theme, and the Mac's appearance picks between them. A preview from ⌘K, Change Theme… takes the place of the theme of its own mode and forces that appearance on the app until it ends. Each `Theme` color is a dynamic `NSColor` that reads the active pair, kept behind a lock, every time AppKit draws it, so colors AppKit views already hold follow a change too. SwiftUI views draw again because reading a `Theme` color registers with the store. The reader gets the colors as CSS variables in a `<style id="jolta-theme">` that `ReaderPage` adds to each page it loads and replaces by script when the theme changes.

The empty inbox takes its colors from the theme too (`Scenery` in `apple/Jolta/Scenery.swift`): a sky and two hills for dawn, day, dusk and night, plus the bolt's colors. Each sky is mixed from the theme's own blue, cyan, green, magenta and orange toward its background or text color. A dark theme's sky stays dark at every hour, so an empty inbox never lights up a dark screen; the hour only tints it. A light theme gets the full day, pale by day and dark at night. Graphite Light keeps its hand-drawn skies. Contrast floors keep the words at 4.5:1 against the sky and the bolt at 4:1. The screen still draws with Core Animation layers and two small Core Graphics images, so a theme change only sets layer colors and redraws those two images.

## MCP

The core runs the MCP server and listens on `jolta.sock` in the app group container while the app runs. It speaks MCP's JSON-RPC directly (one message per line; `initialize`, `tools/list`, `tools/call`, `ping`) instead of using rmcp: tools are all Jolta needs, and the hand-written server avoids rmcp's fast-moving 3.x API. An agent's config points at `Jolta.app/Contents/MacOS/jolta-mcp`, which only copies bytes between stdio and the socket. Tools in the MVP are `search`, `read_thread`, `list_mailboxes`, `create_draft`, `label`, `archive` and `snooze`. Every tool result wraps email content in a block marked as untrusted data. Each agent has grants per account and per tool, and every call is written to `audit`. Sending is not an agent tool; an agent can only create a draft that the user sends.

## Tests

- **Unit tests** sit next to the code they check (`cargo test -p jolta-core`): the query parser, the sanitiser, MIME, AI answer parsing.
- **Regression and journey tests** live in `crates/ffi/tests/regression/` and run with `cargo test -p jolta-ffi --test regression`. Each test opens a fresh data folder in a temporary directory through the same `Core` the Mac app calls, adds accounts without a server (the engine starts no sync for them), imports messages written by the `Mail` builder in `fixture.rs`, and acts as the app would: list, open, archive, undo, reply, send, search. Secrets go to an in-memory store (`secrets::use_memory_store`), so no test touches the Keychain. The whole suite runs offline in well under a second.
- A test that needs state the app has no call for, such as an AI sorting result, writes it through a second `Jolta` handle on the same folder. The app's cached list order doesn't see those writes, so `App::list` pushes the cache out first.
- **Sync tests** (`sync.rs`) run the same app calls against a real IMAP server and SMTP catcher: Dovecot 2.4.5 and Mailpit 1.33.0 in Docker (OrbStack works), started with `scripts/test-servers.sh up` and listening on 127.0.0.1 only. Any user name signs in to the test Dovecot, so each test uses a new one and starts with an empty mailbox. They cover the first sync, IDLE, actions and undo reaching the server, changes made elsewhere arriving, sending through SMTP with the Sent copy, snooze and drafts. Without the containers they skip; `JOLTA_SYNC_TESTS=1` makes a missing server a failure. They take about 20 seconds, mostly the 10-second undo-send window.
- **Live check** (`scripts/live-check.sh <address>...`) runs against real accounts, for what Dovecot can't stand in for: Gmail's labels and Microsoft Graph. Run by hand only. It copies the named accounts into its own data folder (`Jolta/LiveCheck`, same Keychain entries) so no other account syncs, refuses accounts with more than 500 messages, acts only on mail it sends to the account's own address with a random token in the subject, deletes nothing for good (its mail ends in Trash), and fails if any other message's folders or flags changed. Each step has a three-minute limit.

The script also imports `Fixtures/calendar-work.ics` and `calendar-personal.ics` with `jolta cal import`, repeating events that land in every week. When another Jolta runs on the Mac (the installed one), the test instance starts in the background and SwiftUI never presents its window, so the journeys open it from the menu bar item. Run them with `scripts/ui-tests.sh` (optionally naming tests). The test runner is sandboxed and can't write to Jolta's data folder, so the script fills one folder per test, `~/Library/Application Support/Jolta/UITest-<test name>`, from `Fixtures/` with the signed `jolta` CLI (`jolta dev local-account`, then `jolta import`), runs `xcodebuild test`, and removes the folders. The journeys take over the screen's keyboard and mouse for about 30 seconds, and they share the debug app's preferences (such as the list's sort order) with Jolta builds run by hand on the same Mac. macOS needs Automation Mode allowed once per Mac, with an admin password: `sudo automationmodetool enable-automationmode-without-authentication`.
- Schema checks read the schema files themselves: a new `schemaN.sql` missing from `MIGRATIONS` fails `store::old_data_folders_upgrade`, and a new table with an `account_id` column is checked by `accounts::removing_an_account_leaves_nothing_behind` without editing the test.

## Performance budgets

Measured on Apple Silicon with the `jolta` CLI's synthetic mailbox until real mail is available.

- Search: p95 under 100 ms over 100k messages, results updating as you type.
- Memory: the app process under 150 MB with three accounts and one message open. WebKit's WebContent and GPU processes are measured and reported separately.
