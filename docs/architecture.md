# Architecture

How Jolta fits together: the shape the code should have.

## Overview

```
 ┌──────────────────────────── Jolta.app (sandboxed) ─────────────────────────────┐
 │                                                                               │
 │  SwiftUI + AppKit shell (apple/App)                                           │
 │   sidebar · NSTableView message list · reader (one WKWebView) · compose ·     │
 │   Cmd+K palette · settings · agent approvals                                  │
 │        │  async calls, pages of rows             ▲  CoreEvent callbacks       │
 │        ▼                                         │                            │
 │  JoltaFFI Swift package (generated by UniFFI, Swift 5 mode)                    │
 │        │                                                                      │
 │  ┌─────▼──────────────── Rust core (crates/core) ───────────────────────────┐ │
 │  │ accounts/oauth ─ keychain                                                │ │
 │  │ sync: ImapEngine (Gmail, iCloud, Fastmail, IMAP) · GraphEngine (M365)    │ │
 │  │ store: SQLite (WAL) + blob files  ·  search: FTS5 + query language       │ │
 │  │ actions: optimistic apply + op queue + undo · snooze · outbox            │ │
 │  │ render: mail-parser → ammonia + CSS filter → safe HTML                   │ │
 │  │ mcp: server on a Unix socket, permissions, approvals, audit log          │ │
 │  └──────────────────────────────────────────────────────────────────────────┘ │
 │                                                     ▲ Unix socket (app group) │
 │  Contents/MacOS/jolta-mcp  (stdio ⇄ socket bridge) ──┘                         │
 └───────────────────────────────────────────────────────────────────────────────┘
        │ IMAP/SMTP (TLS)          │ HTTPS (Graph, OAuth)         ▲ stdio
        ▼                          ▼                              │
   Gmail, iCloud, Fastmail    Microsoft Graph, Google/Microsoft   AI agents (Claude
   and other IMAP servers     sign-in                             Code, Codex, ...)
```

The core owns all state. The shell renders what the core says and sends user intents back. Nothing in Swift knows what IMAP or Graph is.

## Data model

One model covers Gmail labels, IMAP folders and Graph folders. A message belongs to one account and to any number of mailboxes.

| Table | Holds | Notes |
|---|---|---|
| `account` | id, kind (`imap`, `gmail`, `graph`), address, display name, server settings, sync state | Secrets are in the Keychain, keyed by account id. |
| `mailbox` | id, account, remote id or path, name, role (`inbox`, `sent`, `drafts`, `archive`, `trash`, `spam`, `snoozed`, none), per-mailbox sync cursor | The cursor is `UIDVALIDITY` + highest UID + `HIGHESTMODSEQ` for IMAP, or the delta link for Graph. Gmail labels are mailboxes too. |
| `message` | id, account, remote id, thread id, Message-ID, date, from, to/cc, subject, snippet, flags (seen, flagged, answered, draft), has attachments, size, blob hash, List-Id | Remote id is `X-GM-MSGID` for Gmail, the immutable id for Graph, and `mailbox + UID` for plain IMAP. |
| `message_mailbox` | message, mailbox, UID where relevant | The many-to-many link. Archive in Gmail removes the inbox row; in IMAP it is a move. |
| `thread` | id, account, latest date, subject, participants, unread count | Built from `X-GM-THRID` (Gmail), `conversationId` (Graph), or References / In-Reply-To with a subject fallback (IMAP). |
| `op` | id, account, kind, target ids, payload, state (`pending`, `sent`, `failed`), created, undo deadline | Every user and agent action. Applied to local tables at once, sent to the server by the sync engine, and safe to replay. |
| `snooze` | message or thread, wake time, original mailbox | The message moves to a server folder or label named `Snoozed`, so phones hide it too. The core moves it back at wake time. |
| `outbox` | draft blob, account, send-after time | Undo send is a delay: the message waits here for the undo window, then the engine sends it. |
| `section` | id, name, position, query | Split inbox sections are saved searches in the same query language as search. |
| `agent`, `agent_grant`, `audit` | MCP clients, their permissions, and every action they took | |
| `message_fts` | FTS5, contentless: subject, from, to, body text | Rowid is `message.id`. |

Calendars have their own tables (`calendar`, `event`, `occurrence`), written by `store/calendar.rs`. The views read only `occurrence`.

Invitations in mail (`calendar/invitation.rs`) get one `invitation` row per event that a message's `text/calendar`, `application/ics` or `.ics` part names: its UID, recurrence id, sequence, iTIP method and organizer, written whenever a body is stored (`store/invitations.rs`). A message reaches its event through the UID, so syncs that replace event rows need no update there. Bodies stored before this table existed get one background pass (`engine::scan_invitations`), for mail of the last 400 days. The reader builds an invitation card per event from the message itself (`calendar/card.rs`, HTML in `render/invitation.rs`): times in the Mac's zone, the answer from the calendar's copy, overlaps from `occurrence`, and a warning when the user never wrote to the organizer. Descriptions stay out of the card.

Answering (`calendar/respond.rs`) has one entry for the card and the calendar's detail. `plan` decides who tells the organizer from the source of the event's copy in the calendars of the account the invitation came to; another account's copy may be the organizer's own, when one of the user's accounts invites another.

| Copy | Reply | Don't send a reply |
|---|---|---|
| Google or Microsoft 365 | The provider answers and tells the organizer (`rsvp::answer`) | The provider answers without telling |
| CalDAV | The copy is answered with `SCHEDULE-AGENT=CLIENT`, then Jolta mails the iMIP reply: iCloud doesn't reply to an outside organizer | The copy is answered with `SCHEDULE-AGENT=CLIENT` |
| None, a feed or a calendar on this Mac | Jolta mails the iMIP reply | Nothing goes out |
| EventKit | Refused: macOS doesn't let apps answer for its calendars | Refused |

The reply mail (`rsvp::imip_reply`) goes from the account the invitation came to, only to the organizer, through the outbox with no undo delay. It is built before the provider is asked, so an invitation Jolta can't reply to changes nothing anywhere. The reply answers only as that account, its address or an alias its calendar's copy marks as the user's, never as another of the user's accounts on the same invitation. Every answer is also kept in `invitation_answer` (account, UID, recurrence id), which the card shows when no calendar Jolta answers through holds the event; a whole-series answer replaces the ones kept for single occurrences. The row also keeps the note, the reply choice and the outbox row of the reply mail: the same answer again sends nothing new (a reply still waiting goes at once), and a changed one takes back a reply still waiting. An invitation to one occurrence without its series is always answered for that occurrence.

The message list marks a conversation that carries an invitation (`store::thread_invitations`, one statement per page of rows). The invitation it shows is its newest message from the organizer, else its newest reply. A request shows the answer its card shows (`store::shown_answer`), for a series the answer to the occurrence the card shows, the next one still to come (`series::shown_occurrence`, from the series and changed occurrences the `timing` column keeps), "Not answered" while its event is still to come, and the mark alone once it has passed unanswered; a cancellation, or a request whose event a cancellation with the same or a later SEQUENCE ended, shows "Cancelled"; replies and the user's own meetings show the mark alone. Each `invitation` row keeps when its event ends (for a series its last occurrence, or never for a rule without UNTIL or COUNT). `is:invite` finds the conversations whose invitation shows "Not answered" (`store::unanswered_threads` asks `thread_invitations`), so `-is:invite` finds exactly the others. An answer or a calendar change drops the app's cached list order and redraws the list, and so does the moment a "Not answered" event ends or a series moves on to its next occurrence (`store::next_invitation_change`), through a timer in the bridge. On the Mac mini's copy of a 168,000-message store, the first page of all mail took 0.84 ms p95 before and 0.87 ms after; a conversation with an invitation costs about 9 µs more, and one showing a repeating request about 18 µs more again, for placing its occurrences.

An organizer's update is a new invitation mail with the same UID (`calendar/update.rs`). Versions are ordered by SEQUENCE, then DTSTAMP. Only the meeting's organizer makes versions: the organizer is the one on the account's calendar copy, else on the first request for the UID to arrive, by the date the server received it, that came from its own organizer, and a mail counts when it names that organizer and comes from that address, from `calendar-notification@google.com` or iCloud's `noreply@email.apple.com`, or, for the user's own meeting, from another of the user's addresses. A request or cancellation without an ORGANIZER fails it. A message that fails this changes no other card, offers no answers or removal, and its card says "This isn't from the meeting's organizer". The card compares a message with the account's other mails for the same event or occurrence (`invitation` rows, bodies read from the blob store), with cancellations of the whole series for an occurrence, and with the account's calendar copy. A newer version in either makes the card say so, with no answers, conflicts or Join: a copy with a higher SEQUENCE whatever it changed, and a cancelled copy as a cancellation (on Graph, which keeps no SEQUENCE, only that). An occurrence's invitation also reads as cancelled once the copy of its series is cancelled. Otherwise the version before it is the latest earlier request, or the copy while its SEQUENCE is lower (on Graph another time counts, and only while no newer mail exists). Repeat rules compare by meaning (`recur::same_repeat`), so Graph's rule without `INTERVAL=1` equals the mail's with it, and two UNTILs that keep the same last occurrence are equal. For an occurrence moved for the first time, it is where the series had that occurrence. The card strikes through what changed against that version (`Changes`): the time, keeping the day when only the time moved and the other way round, the repeat rule, the place and the meeting link. An answer given to an earlier version holds unless the time, the day or the repeat rule changed since (`update::answer_holds`). A provider copy is judged against its own SEQUENCE, so after a sync it shows what Google or Microsoft 365 decided, and both reset answers on a move. An answer kept in `invitation_answer` is judged by the reply mail that sent it, which names the version, and for a series by the repeat rule of the request it answered. A series answer shown on a changed occurrence, from a reply mail or a provider's copy of the series, also holds only while that occurrence stays where the series has it. An answer given with "Don't send a reply" has no reply mail, so it holds across a move.

A cancellation's card offers Remove from calendar while the receiving account's calendar holds the event, or the cancelled occurrence, uncancelled, as the user's copy as a guest: in a calendar the account owns (on CalDAV, one whose DAV:owner is the account's principal, else one with the `all` privilege), listing the user as an attendee, and organized by someone else than the account or an alias the copy or the CalDAV principal names. Deleting the organizer's copy on Microsoft 365 would cancel the meeting for every guest, so `remove::guest_copy` refuses it before any request. `calendar/remove.rs` routes it per provider. Google and Microsoft 365 are asked first and only resynced when they already removed or cancelled the event, which both do within a minute. Otherwise the copy is deleted with `sendUpdates=none` on Google or a plain DELETE on Graph. A CalDAV copy gets SCHEDULE-AGENT=CLIENT on its ORGANIZER, then a DELETE, or an EXDATE for one occurrence, each with `If-Match`, so a scheduling server tells nobody. A 412 from any provider means the copy changed since Jolta read it, perhaps reinstated, so Jolta resyncs the calendar and says "The meeting changed; check it again" instead of trying again. Every CalDAV write carries an ETag. A copy fetched again, because the stored one has no ETag or the PUT returned none, is deleted only while it keeps the SEQUENCE and status Jolta read, and a server that gives no ETag gets the copy left alone with a message saying so.

Raw RFC 822 messages are stored as files in the data folder (`~/Library/Application Support/Jolta/blobs`), named by SHA-256. The SQLite file sits next to them, outside the app group container, because macOS keeps the unsandboxed `jolta` CLI out of that container; the sandboxed app reaches the folder through a `home-relative-path` exception. Headers and snippets go to SQLite on first sync; bodies download on demand and in the background for recent mail.

## Sync

Each account runs one engine task on tokio. Both engines implement the same small interface.

```rust
trait Engine {
    async fn run(&self, ctx: SyncCtx) -> Result<()>;      // initial sync, then keep up to date
    async fn apply(&self, op: &Op) -> Result<OpOutcome>;  // push one queued local change
    async fn fetch_body(&self, msg: &MessageRef) -> Result<Blob>;
    async fn send(&self, draft: &OutboxItem) -> Result<()>;
}
```

- **Plain IMAP.** Sync INBOX first, newest messages first, so the list fills within seconds; other folders follow. Use CONDSTORE (`CHANGEDSINCE`) when offered, QRESYNC when offered, and otherwise a UID range fetch plus a flag sweep over recent UIDs. One extra connection holds IDLE on INBOX. A changed `UIDVALIDITY` drops and refetches that mailbox.
- **Gmail.** Same IMAP engine with Gmail mode on: sync `[Gmail]/All Mail` only and read labels from `X-GM-LABELS`, so a message in three labels is stored once. Thread ids come from `X-GM-THRID`. Gmail search operators can be passed to the server through `X-GM-RAW` when local search lacks the mail.
- **Microsoft Graph.** One delta query per mail folder with immutable ids, polled every 30 to 60 seconds and right after any local action. Sending uses `sendMail`; drafts use the drafts API. Throttling (HTTP 429) honours `Retry-After`. An admin-consent error during sign-in shows as a plain message with the tenant name.
- **Offline and failures.** Ops queue while offline and replay in order when the connection returns. A failed op is retried with backoff; after it fails for good, the local change is reverted and the UI shows why.

## The bridge to Swift

Keep the UniFFI surface small and coarse. Lists cross as pages, never whole mailboxes.

- `Core::open(data_dir, listener) -> Core`
- `accounts()`, `add_imap_account(...)`, `begin_oauth(provider) -> url`, `remove_account(id)`
- `query_count(query) -> u32` and `query_page(query, offset, limit) -> Vec<ThreadRow>` for any list: an account's inbox, the unified inbox, a section, a search
- `open_thread(id) -> ThreadDetail` with sanitized HTML per message
- `perform(action, target) -> UndoToken` and `undo(token)`
- `compose(...)`, `send(draft) -> UndoToken`
- `snooze(target, until)`, sections CRUD
- `vips()` and `set_vips(addresses, vip)`. Rows and reader messages carry a `vip` flag, and new-mail events say whether the sender is a VIP, so the app can limit banners to VIPs.
- `suggest_addresses(typed, account, recipients)`, `forget_address`, `set_address_book`: compose suggestions from people you sent to or replied to, ranked by how often and how recently, with mail from the chosen account counting double. The list is built from the store (about 80 ms for 23,000 sent messages), cached, and rebuilt in the background when older than two minutes. The app may hand over the Mac's Contacts as a lower-ranked source; they never leave the process.
- `unsubscribe(thread)` reads `List-Unsubscribe` from the message source and leaves the list: an RFC 8058 one-click POST when offered over HTTPS, else an unsubscribe email from the receiving account through the outbox, else the web page for the app to open.
- Message bodies cross the bridge as one string in a small Markdown subset (`rich.rs`: bold, italic, strikethrough, links, list and quote lines). The editor converts with `body_spans` and `body_markdown`; `compose::build` sends a plain-text part and an HTML part made from it. Each account's signature (`set_signature`) is in the same format, and `swap_signature` replaces it when the sender changes.
- `send(compose, send_at, remind_at)`: `send_at` holds the message in the outbox until then (the engine already wakes for the next queued send; `scheduled()` lists them, `cancel_send` takes one back for editing). `remind_at` stores a reminder by the message's Message-ID. When it is due and nobody but the user's own accounts has written in the thread since, the reminder fires: `CoreEvent::NoReply`, and inbox lists include the thread (`search::reminder_queries` reruns the list's query for that thread) until it is archived, trashed, moved or snoozed. Nothing changes on the server. Both need Jolta running at that time; otherwise they happen at the next launch.
- `reply_compose(thread, Forward)` saves the original's attachments under `<data dir>/forwards/<message id>/` and lists them on the compose. Images the HTML shows inline stay behind.
- AI (`core/src/ai`, bridge in `ffi/src/ai.rs`), off until the user picks a model in Settings › AI:
  - `ai_settings()`, `set_ai_settings(...)`, `set_ai_key(provider, key)`: the provider (this Mac, OpenAI or Anthropic), the model, an optional API address per provider and whether long conversations get a summary as they open. Settings live in the `setting` table under `ai`; API keys in the Keychain as `ai:openai` and `ai:anthropic`, never back across the bridge.
  - `ai_models(provider, url, key)` lists the provider's models and so checks the key and address. OpenAI-compatible servers use the Responses API (`POST {url}/responses`), Anthropic-compatible ones the Messages API (`POST {url}/v1/messages`), both streamed over server-sent events.
  - `local_models()`, `download_model(id)`, `pause_download(id)`, `remove_model(id)`: the catalog in `ai/local.rs` (Gemma 4 E2B, the default, and E4B), downloaded from Hugging Face into `<data dir>/models`, resumable with an HTTP range, renamed into place only after its SHA-256 matches. Progress arrives as `CoreEvent::ModelChanged`.
  - `summarize(thread, automatic, fresh, listener) -> AiTask` and `draft_message(compose, instruction, listener) -> AiTask` stream through `AiListener` (phase, all text so far, outcome); `AiTask.cancel()` stops them. `with_written(body, account, text)` puts a draft in front of the signature and quote.
  - Summaries are made only when a conversation is opened (automatically for 3 or more messages or 2,500 characters of text), never for old mail in bulk, and kept in `ai_summary` with the newest message they cover. A summary that new messages made stale is updated from the old summary plus the new messages: 1.5 s instead of 5.2 s for the 21-message test thread on the mini.
  - Sorting (`ai/triage.rs`): each incoming inbox message gets a category (personal, work, finance, newsletter, notification) and a needs-reply flag in `ai_triage`, once. The local model answers in two lines held to a GBNF grammar, about 0.4 s a message on the mini. `is:needs-reply` matches a conversation whose newest message was flagged and isn't answered; `category:<name>` matches a category. List rows carry `needs_reply` for the reply arrow. On by default for the model on this Mac, off for cloud providers.
  - Background queue (`ai/background.rs`): one job at a time, sorting before summaries. New mail queues its unsorted messages, and its conversation for a summary when that is long and the model is on this Mac. Every start, and switching sorting on, queue the unsorted inbox mail of the last 14 days. With the local model the queue waits while the app reports battery power, Low Power Mode or a hot Mac (`set_ai_background_allowed`, from `Power.swift`).
  - Search with AI (`ai/search.rs`, `ai_search_query`): ⌘J in the search field turns a request into a query in Jolta's search language, which replaces the typed text and runs over all mail. Relative dates ("last week", "vorige maand") are worked out in code and handed to the model, and the parser checks the answer, with one retry.
  - The local model runs in `jolta-ai`, which the core starts on first use and stops after 5 idle minutes. It speaks one JSON object per line over stdin and stdout (`load`, `generate`, `cancel`; `loaded`, `reading`, `text`, `done`, `error`); the core formats Gemma 4's chat prompt with thinking off. It inherits the app's sandbox and is built only for Apple silicon; on Intel it answers every request with an error and the settings offer the cloud providers.
- Calendar (`core/src/calendar`, bridge in `ffi/src/calendar.rs`). Swift does no calendar logic: times cross as unix seconds, all-day events as `YYYY-MM-DD` days, so Swift never moves an all-day event between zones.
  - `calendars()` lists every account with its calendar switch and calendars, then the calendars of no account (feeds, local). Each calendar has its kind, access, color, shown, counts as busy, notify, event count, last sync time and last sync error.
  - `set_calendar_enabled(account, on)` turns calendar on (lists the account's calendars, shows the primary one and syncs it) or off (deletes the account's calendar data here, never on the server). Google and Microsoft accounts need calendar consent first (`needs_consent` in `calendars()`): `begin_calendar_consent(account)` returns the same `SignIn` as adding an account, and its `finish()` keeps the new refresh token in the account's Keychain entry, turns calendar on and asks the calendar task to sync the shown calendars.
  - `set_calendar_shown`, `set_calendar_busy`, `set_calendar_notify`, `set_calendar_color`. Showing a calendar syncs it; a hidden one isn't synced and leaves every view.
  - `subscribe_calendar(url)` adds a `webcal://` or `https://` feed and returns after its first download. `remove_calendar(id)` removes a feed or local calendar; an account's calendars go with the account's switch.
  - `calendar_occurrences(from, to)` returns the occurrences on the days from `from` through `to - 1` in the Mac's zone, all-day events first. Pass the midnights the Mac's calendar gives: a week across a clock change is an hour shorter or longer than 7 × 86,400 seconds. One week of the synthetic calendar (422 occurrences) takes 0.53 ms p50 and 0.59 ms p95 on the Mac mini, records and UniFFI's buffer included (`week_query_through_the_bridge`, ignored, run with `--release`).
  - `calendar_event(event, time, app_css)` is one occurrence's detail: its times in the event's own zone and here ("10:00 to 11:00 New York (16:00 to 17:00 here)"), the repeat rule in words, the description as a sanitised document (the mail pipeline: ammonia, the CSS filter, blocked remote images, the CSP), the organizer, attendees grouped by response with comments and a summary ("2 accepted, 1 maybe, 1 no answer"), rooms, the meeting (join link, app link, phones, meeting id, passcode) and the alarms.
  - `remove_cancelled(message)` runs a cancellation card's Remove from calendar through `remove::remove` and returns the toast's words ("Removed from your calendar.").
  - `answer_invitation(message, answer, options)` answers the card on a message and `answer_event(event, time, answer, options)` an event from its detail, both through `respond::answer`. The options are a note, `notify` (false for "Don't send a reply") and `occurrence_only`, which answers the occurrence the card or detail shows. They return the toast's words ("Accepted. Jolta emailed Ann."), wake the account whose outbox holds a reply mail and report the changed calendar. `ThreadView.invitations` lists the conversation's answerable invitations, each with whether its message starts expanded; Y, M and N answer the last one whose message is expanded; `EventDetail.can_answer` says whether the detail offers answers.
  - `calendar_reminders(from, to)` lists the alarms that go off in that range, from shown calendars with notifications on, without declined events or email alarms. Each has an id made from the calendar, the event's UID, the occurrence start and the trigger, so a sync that rewrites the rows keeps it and the app can replace scheduled notifications by id. Alarms more than 4 weeks ahead of their event aren't found.
  - `next_meeting(now)` is the online meeting to join: one starting within 10 minutes, else the one running that started last, else the next within a week.
  - The engine's calendar task (`calendar/scheduler.rs`) syncs every shown calendar of enabled accounts every 5 minutes and after `sync_now`, and feeds at their refresh interval, four at a time; a failing calendar backs off alone, from a minute up to its interval. Each round it rebuilds every series from the stored events when the occurrence window start (kept in `setting` as `calendar_occurrences`) is more than 30 days behind, or when the Mac's zone differs from the one the occurrences were built in, because floating events depend on it.
  - `CoreEvent::CalendarChanged { calendar_ids }` says which calendars' occurrences changed, after syncs, rebuilds and settings; the app redraws and reschedules reminders. `CoreEvent::CalendarSynced { calendar_id, error }` ends every sync attempt.
- The app's side of the calendar (`apple/Jolta/Calendar*.swift`, `EventDetail.swift`, `DayPanel.swift`) draws what the core returns and keeps no calendar rules:
  - `AppModel.mode` switches between mail (⌘1) and calendar mode (⌘2). `CalendarModel` holds the span (day, work week, week, month, agenda), the period's days as the Mac's midnights, its occurrences, the selection and the open detail. A key that moves the period reads one `calendar_occurrences` call; the periods before and after are read ahead off the main thread, so J and K usually find their week already read.
  - The day, work week and week views and the day panel are one AppKit view, `CalendarWeekView`: a strip with day names and all-day lanes, and an `NSScrollView` over a full day whose document view draws nothing. One view the size of the visible area follows the scrolling and draws the shading outside 09:00 to 18:00, the hour lines and labels, the events and the current time. The model updates it directly on every change instead of through SwiftUI, so a week switch draws inside the key's own run-loop pass. Measured on the Mac mini (synthetic calendar, about 420 occurrences a week, optimized build, keys 60 ms apart, `-JoltaCalBench YES`): key to drawn 11.5 to 12.4 ms p50 and 14.6 to 17.1 ms p95. SwiftUI `Canvas` was measured against it first and lost: 64 ms against 18.8 ms to draw one week's events. Memory with a week open settles 11 MB above mail with a conversation open when Jolta starts in calendar mode, and 30 to 45 MB above mail after switching from it. The first draw also takes about 115 MB of GPU memory that macOS marks reclaimable within two seconds and takes back within ten; a CPU bitmap instead kept three copies of the picture and drew slower.
  - Overlapping events share the column width (`CalendarLayout.timed`, column packing per group of overlaps). All-day and day-long events sit in lanes above the hours. Calendar colors are the only color besides the accent: `CalendarColor` moves a calendar's color toward the theme's text until it reads on the theme's background, and mixes its fills from the background, so all 27 themes work.
  - The event detail comes from `calendar_event`; the description shows in a `ReaderPage`, the mail reader's locked-down web view. Every event is an accessibility button with a full label ("Standup, 9:30 to 9:45, Microsoft Teams meeting, accepted").
  - Reminders: `Notifier.schedule(reminders:)` keeps the next 48 hours of `calendar_reminders` pending as calendar-triggered notifications under `cal-<record id>`, replacing by id and removing the ones no longer listed, at launch, on `CalendarChanged` and hourly. They fire with Jolta closed. Actions: Join (online meetings), Snooze 5 Minutes, Open. macOS 27 keeps 100 pending notifications per app and pushes one out for each added past that (measured 2026-11-04), so Jolta schedules at most 90.
  - Join opens the meeting's `app_url` when `NSWorkspace.urlForApplication(toOpen:)` finds the app, else the https link; it is the accent from 5 minutes before the start until the end. ⇧⌘J and the palette's Join next meeting use `next_meeting`; the menu bar item counts down to it within the hour before it ("Standup in 12 min").
  - `webcal://` links open in Jolta (`CFBundleURLTypes`; Settings › Calendar can make Jolta their default app) and subscribe after a confirmation.
- The invitation card's buttons are `x-rsvp:<message>/<accept|maybe|decline|note|quiet|scope|remove>` links that the reader's navigation decider hands to Swift, like `x-attachment:`. The app keeps the open card's choices (`AnswerChoices`) and marks them, and an answer going out, on the page with its own script, since the page runs none. "Add a note" and the series scope open small panels drawn in the reader's window under their links, not popovers or menus, so nothing modal opens. A user script in the app's own script world reports each message's expand and collapse through a script message handler; the app keeps them for Y, M, N and the palette, and sets them again when the page reloads after an answer.
- `CoreListener.on_event(CoreEvent)`: list changed (with query ids), sync status, new mail, agent approval request, calendar changes, errors

The Swift side keeps a page cache per visible list and asks for rows by index as the table scrolls.

## Rendering a message

1. `mail-parser` reads the raw message and picks the HTML part, or converts plain text to HTML.
2. `ammonia` strips scripts, event handlers, forms, iframes, objects, embeds, `javascript:` links and meta refresh.
3. Our CSS filter cleans `<style>` blocks and style attributes: no `@import`, no remote `url()`, no attribute-selector tricks.
4. Remote URLs are rewritten to `x-remote:` and inline parts to `cid:`. Remote images stay blocked until the user allows them for that sender or message; then the core fetches them without cookies or referrer and hands the bytes to the web view.
5. The web view loads the result with JavaScript off, subresource loading off, a CSP meta tag, a block-all content rule list, and a navigation decider that opens clicked links in the browser only after showing the real destination.

## Themes

The app draws with 16 color tokens (`ThemeTokens` in `apple/Jolta/ThemePalette.swift`). Graphite Dark and Graphite Light are written out by hand. The 25 Omarchy-format themes are mixed from Omarchy's `colors.toml` files, which `python3 scripts/omarchy-themes.py <omarchy checkout>` copies into the generated `apple/Jolta/OmarchyThemes.swift` with Omarchy's MIT notice; rerun it by hand when Omarchy changes. The script also reads `scripts/themes/`, which holds themes Omarchy doesn't ship in Omarchy's format: Catppuccin Frappé and Macchiato, from Catppuccin's palette with its MIT license, mapped onto Omarchy's names the way Omarchy maps Mocha. `ThemeStore` saves a dark and a light theme, and the Mac's appearance picks between them. A preview from ⌘K, Change Theme… takes the place of the theme of its own mode and forces that appearance on the app until it ends. Each `Theme` color is a dynamic `NSColor` that reads the active pair, kept behind a lock, every time AppKit draws it, so colors AppKit views already hold follow a change too. SwiftUI views draw again because reading a `Theme` color registers with the store. The reader gets the colors as CSS variables in a `<style id="jolta-theme">` that `ReaderPage` adds to each page it loads and replaces by script when the theme changes.

The empty inbox takes its colors from the theme too (`Scenery` in `apple/Jolta/Scenery.swift`): a sky and two hills for dawn, day, dusk and night, plus the bolt's colors. Each sky is mixed from the theme's own blue, cyan, green, magenta and orange toward its background or text color. A dark theme's sky stays dark at every hour, so an empty inbox never lights up a dark screen; the hour only tints it. A light theme gets the full day, pale by day and dark at night. Graphite Light keeps its hand-drawn skies. Contrast floors keep the words at 4.5:1 against the sky and the bolt at 4:1. The screen still draws with Core Animation layers and two small Core Graphics images, so a theme change only sets layer colors and redraws those two images.

## MCP

The core runs the MCP server and listens on `jolta.sock` in the app group container while the app runs. It speaks MCP's JSON-RPC directly (one message per line; `initialize`, `tools/list`, `tools/call`, `ping`) instead of using rmcp: tools are all Jolta needs, and the hand-written server avoids rmcp's fast-moving 3.x API. An agent's config points at `Jolta.app/Contents/MacOS/jolta-mcp`, which only copies bytes between stdio and the socket. Tools in the MVP are `search`, `read_thread`, `list_mailboxes`, `create_draft`, `label`, `archive` and `snooze`. Every tool result wraps email content in a block marked as untrusted data. Each agent has grants per account and per tool, and every call is written to `audit`. Sending is not an agent tool; an agent can only create a draft that the user sends.

## Tests

- **Unit tests** sit next to the code they check (`cargo test -p jolta-core`): the query parser, the sanitiser, MIME, AI answer parsing.
- **Regression and journey tests** live in `crates/ffi/tests/regression/` and run with `cargo test -p jolta-ffi --test regression`. Each test opens a fresh data folder in a temporary directory through the same `Core` the Mac app calls, adds accounts without a server (the engine starts no sync for them), imports messages written by the `Mail` builder in `fixture.rs`, and acts as the app would: list, open, archive, undo, reply, send, search. Secrets go to an in-memory store (`secrets::use_memory_store`), so no test touches the Keychain. The whole suite runs offline in well under a second.
- A test that needs state the app has no call for, such as an AI sorting result, writes it through a second `Jolta` handle on the same folder. The app's cached list order doesn't see those writes, so `App::list` pushes the cache out first.
- **Sync tests** (`sync.rs`) run the same app calls against a real IMAP server and SMTP catcher: Dovecot 2.4.5 and Mailpit 1.33.0 in Docker (OrbStack works), started with `scripts/test-servers.sh up` and listening on 127.0.0.1 only. Any user name signs in to the test Dovecot, so each test uses a new one and starts with an empty mailbox. They cover the first sync, IDLE, actions and undo reaching the server, changes made elsewhere arriving, sending through SMTP with the Sent copy, snooze and drafts. Without the containers they skip; `JOLTA_SYNC_TESTS=1` makes a missing server a failure. They take about 20 seconds, mostly the 10-second undo-send window.
- **Live check** (`scripts/live-check.sh <address>...`) runs against real accounts, for what Dovecot can't stand in for: Gmail's labels and Microsoft Graph. Run by hand only. It copies the named accounts into its own data folder (`Jolta/LiveCheck`, same Keychain entries) so no other account syncs, refuses accounts with more than 500 messages, acts only on mail it sends to the account's own address with a random token in the subject, deletes nothing for good (its mail ends in Trash), and fails if any other message's folders or flags changed. Each step has a three-minute limit.
- **UI journeys** (`apple/JoltaUITests/`) drive the real app with XCUITest: archive and undo with keys, opening a conversation, the palette keeping the keyboard, search, and the calendar's keys (⌘2, J and K, Return on an event, a calendar's number). The script also imports `Fixtures/calendar-work.ics` and `calendar-personal.ics` with `jolta cal import`, repeating events that land in every week. When another Jolta runs on the Mac (the installed one), the test instance starts in the background and SwiftUI never presents its window, so the journeys open it from the menu bar item. Run them with `scripts/ui-tests.sh` (optionally naming tests). The test runner is sandboxed and can't write to Jolta's data folder, so the script fills one folder per test, `~/Library/Application Support/Jolta/UITest-<test name>`, from `Fixtures/` with the signed `jolta` CLI (`jolta dev local-account`, then `jolta import`), runs `xcodebuild test`, and removes the folders. Each test launches Jolta with `-JoltaTestData UITest-<test name>`; run without the script, the tests skip. The full log goes to `/tmp/jolta-ui-tests.log`. The journeys take over the screen's keyboard and mouse for about 30 seconds, and they share the debug app's preferences (such as the list's sort order) with Jolta builds run by hand on the same Mac. macOS needs Automation Mode allowed once per Mac, with an admin password: `sudo automationmodetool enable-automationmode-without-authentication`.
- Schema checks read the schema files themselves: a new `schemaN.sql` missing from `MIGRATIONS` fails `store::old_data_folders_upgrade`, and a new table with an `account_id` column is checked by `accounts::removing_an_account_leaves_nothing_behind` without editing the test.

## Performance budgets

Measured on Apple Silicon with the `jolta` CLI's synthetic mailbox until real mail is available.

- Cold start to a usable inbox: under 500 ms with 100k messages.
- Opening a cached message: under 50 ms.
- Search: p95 under 100 ms over 100k messages, results updating as you type.
- Memory: the app process under 150 MB with three accounts and one message open. WebKit's WebContent and GPU processes are measured and reported separately.
- The UI thread never waits on the network or on SQLite writes.
